## 1. 知识图谱 vs 向量数据库：互补而非替代

### 1.1 核心差异

| 维度 | 向量数据库 | 知识图谱 |
|------|----------|---------|
| 数据表示 | 稠密向量 (连续空间) | 三元组 (离散符号) |
| 关系建模 | 隐式 (通过距离) | 显式 (通过边) |
| 查询方式 | 相似度搜索 | 图遍历/SPARQL/Cypher |
| 推理能力 | 无 (黑盒匹配) | 符号推理/规则推导 |
| 可解释性 | 低 | 高 (可追溯路径) |
| 更新成本 | 低 (增删向量) | 中 (需维护关系一致性) |
| 典型场景 | 语义搜索、推荐 | 知识问答、因果分析、实体链接 |

### 1.2 组合架构：GraphRAG

```

                    │     用户查询          │
```

## 2. 本体设计

### 2.1 本体 = 概念模型 + 关系约束

```yaml
# 本体设计示例：科技公司知识图谱
ontology:
  entity_types:
    Company:
      properties:
        - name: string(unique)
        - founded_year: integer
        - headquarters: string
        - market_cap: float
        - industry: string
      
    Product:
      properties:
        - name: string
        - category: [Hardware, Software, Service, Platform]
        - launch_date: date
        - revenue: float
      
    Person:
      properties:
        - name: string
        - title: string
        - expertise: list[string]
      
    Technology:
      properties:
        - name: string
        - maturity: [Research, Emerging, Mature, Declining]
        - category: [AI, Cloud, Security, Database, ...]
      
    Patent:
      properties:
        - patent_id: string(unique)
        - title: string
        - filing_date: date
        - status: [Pending, Granted, Expired]
  
  relationships:
    COMPANY_OWNS_PRODUCT:
      from: Company
      to: Product
      properties:
        - acquisition_date: date
    
    PERSON_WORKS_AT:
      from: Person
      to: Company
      properties:
        - start_date: date
        - role: string
    
    COMPANY_DEVELOPS_TECHNOLOGY:
      from: Company
      to: Technology
      properties:
        - investment_level: [Low, Medium, High]
    
    PRODUCT_USES_TECHNOLOGY:
      from: Product
      to: Technology
    
    COMPANY_FILES_PATENT:
      from: Company
      to: Patent
      properties:
        - inventors: list[string]
    
    PERSON_INVENTED:
      from: Person
      to: Patent
    
    COMPANY_COMPETES_WITH:
      from: Company
      to: Company
      properties:
        - intensity: [Direct, Indirect, Potential]
    
    COMPANY_ACQUIRED:
      from: Company
      to: Company
      properties:
        - acquisition_date: date
        - amount: float
```

### 2.2 本体设计原则

```
1. 单一职责: 每个实体类型只表示一类事物
2. 层次清晰: 使用继承关系减少冗余 (Person → Employee → Engineer)
3. 关系语义化: 动词化命名 (WORKS_AT > HAS_EMPLOYEE)
4. 避免过度设计: 先构建MVP本体，迭代扩展
5. 考虑推理: 定义可传递关系 (parent_of + parent_of → grandparent_of)
6. 属性原子化: address = {street, city, country} 而非一个字符串
```

## 3. 图数据库选型

### 3.1 核心对比

| 维度 | Neo4j | JanusGraph | NebulaGraph | ArangoDB |
|------|-------|-----------|-------------|---------|
| **类型** | 原生图 | 分布式图 | 分布式图 | 多模型 |
| **查询语言** | Cypher | Gremlin | nGQL | AQL |
| **存储后端** | 自研 | HBase/Cassandra/BigTable | 自研(RocksDB) | 自研 |
| **扩展性** | 垂直 (集群版付费) | 水平 (强) | 水平 (强) | 水平 |
| **一致性** | ACID | 最终一致性 | 最终/强一致 | ACID |
| **社区版** | 功能丰富 | 完全开源 | 完全开源 | 完全开源 |
| **图算法** | GDS库 (最全) | 需自行集成 | 基础内置 | 基础内置 |
| **中文社区** | 中等 | 弱 | 强（国产） | 中等 |
| **适合规模** | < 10亿节点 | > 100亿节点 | > 100亿节点 | 中等 |

## 4. 图谱构建ETL管道

### 4.1 全链路构建流程

```python
class KnowledgeGraphBuilder:
    """知识图谱构建管道"""

    def __init__(self, graph_db, embedding_model, llm):
        self.graph = graph_db          # Neo4j / NebulaGraph
        self.embedder = embedding_model
        self.llm = llm                 # 用于实体/关系抽取

    def build_pipeline(self, documents: List[str]) -> dict:
        """从文档到图谱的完整管道"""
        report = {}

        # Stage 1: 实体抽取
        entities = self._extract_entities(documents)
        report["entities_extracted"] = len(entities)

        # Stage 2: 实体消歧 & 链接
        resolved = self._resolve_entities(entities)
        report["entities_resolved"] = len(resolved)
        report["duplicates_merged"] = len(entities) - len(resolved)

        # Stage 3: 关系抽取
        relations = self._extract_relations(documents, resolved)
        report["relations_extracted"] = len(relations)

        # Stage 4: 写入图数据库
        self._write_to_graph(resolved, relations)
        report["nodes_inserted"] = len(resolved)
        report["edges_inserted"] = len(relations)

        # Stage 5: 质量验证
        quality = self._validate_quality()
        report["quality_score"] = quality

        return report

    def _extract_entities(self, docs: List[str]) -> List[dict]:
        """使用LLM抽取实体"""
        prompt = """从以下文本中抽取实体，返回JSON格式。
实体类型: PERSON（人物）, ORG（组织）, PRODUCT（产品）, TECHNOLOGY（技术）, EVENT（事件）, LOCATION（地点）, DATE（日期）

对于每个实体，提供:
- name: 实体名称
- type: 实体类型
- aliases: 别名列表
- context: 实体出现的上下文句子
- properties: 关键属性（如CEO、成立年份等）

文本: {text}

返回格式:
{{"entities": [{{"name": "...", "type": "...", ...}}]}}
"""
        all_entities = []
        for doc in docs:
            response = self.llm.generate(prompt.format(text=doc[:3000]))
            try:
                data = json.loads(response)
                all_entities.extend(data.get("entities", []))
            except json.JSONDecodeError:
                continue
        return all_entities

    def _resolve_entities(self, entities: List[dict]) -> List[dict]:
        """实体消歧：合并指向同一现实实体的不同提及"""
        resolved = []
        for entity in entities:
            # 1. 精确匹配（名称完全相同）
            existing = self._find_exact_match(entity, resolved)
            if existing:
                existing["aliases"].extend(entity.get("aliases", []))
                existing["mentions"].append(entity.get("context", ""))
                continue

            # 2. 模糊匹配（嵌入相似度 + 类型相同）
            existing = self._find_fuzzy_match(entity, resolved)
            if existing and existing["similarity"] > 0.92:
                target = existing["entity"]
                target["aliases"].extend(entity.get("aliases", []))
                target["mentions"].append(entity.get("context", ""))
                continue

            # 3. 新增实体
            entity["mentions"] = [entity.get("context", "")]
            resolved.append(entity)

        return resolved

    def _extract_relations(self, docs, entities) -> List[dict]:
        """抽取实体间的关系"""
        entity_names = [e["name"] for e in entities]

        prompt = """从以下文本中，识别以下实体之间的关系。

已知实体: {entities}

文本: {text}

对于每一对存在关系的实体，提供:
- subject: 主体实体名称
- relation: 关系类型 (WORKS_FOR, LOCATED_IN, FOUNDED, ACQUIRED, COMPETES_WITH, DEVELOPS, PART_OF, ...)
- object: 客体实体名称
- evidence: 支持该关系的原文句子

返回格式:
{{"relations": [{{"subject": "...", "relation": "...", ...}}]}}
"""
        # 分批处理
        all_relations = []
        for doc in docs:
            response = self.llm.generate(
                prompt.format(
                    entities=", ".join(entity_names[:50]),
                    text=doc[:3000]
                )
            )
            try:
                data = json.loads(response)
                all_relations.extend(data.get("relations", []))
            except:
                continue

        return all_relations
```

### 4.2 增量更新策略

```python
class IncrementalKGUpdater:
    """知识图谱增量更新"""

    def __init__(self, graph):
        self.graph = graph

    def add_new_knowledge(self, text: str):
        """增量添加新知识"""
        # 1. 抽取新实体和关系
        entities = self._extract_entities(text)
        relations = self._extract_relations(text, entities)

        # 2. MERGE: 已存在的更新，不存在的创建
        for entity in entities:
            self.graph.run("""
                MERGE (e:Entity {name: $name})
                ON CREATE SET e += $props, e.created_at = datetime()
                ON MATCH SET e.updated_at = datetime(), e.mentions = e.mentions + 1
            """, name=entity["name"], props=entity.get("properties", {}))

        # 3. 创建或更新关系
        for rel in relations:
            self.graph.run("""
                MATCH (s:Entity {name: $subject})
                MATCH (o:Entity {name: $object})
                MERGE (s)-[r:RELATES {type: $type}]->(o)
                ON CREATE SET r.created_at = datetime(), r.evidence = [$evidence]
                ON MATCH SET r.evidence = r.evidence + $evidence, r.updated_at = datetime()
            """, subject=rel["subject"], object=rel["object"],
                 type=rel["relation"], evidence=rel["evidence"])
```

## 5. GraphRAG 深度集成

### 5.1 Microsoft GraphRAG 原理

```
GraphRAG工作流程:

文档索引阶段（离线）:
1. 文本切分 → Source Documents
2. 实体&关系抽取 → Entity Graph
3. 社区检测 (Leiden算法) → Communities
4. 社区摘要生成 (LLM) → Community Summaries

查询阶段（在线）:
├── 全局查询 (Global Search):
│   └── 利用社区摘要进行宏观理解
│       "AI芯片行业的整体竞争格局如何？"
│
└── 局部查询 (Local Search):
    └── 利用实体关系图进行精确推理
        "英伟达与AMD在数据中心GPU市场的竞争关系？"
```

### 5.3 自定义GraphRAG实现

```python
class CustomGraphRAG:
    """自建GraphRAG管线"""

    def __init__(self, graph_db, vector_db, llm):
        self.graph = graph_db      # Neo4j
        self.vector = vector_db    # Qdrant/Milvus
        self.llm = llm

    def global_search(self, query: str) -> str:
        """全局搜索：基于社区摘要"""
        # 1. 找到相关社区
        query_emb = self.embedder.encode(query)
        relevant_communities = self.vector.search(
            query_emb,
            namespace="community_summaries",
            limit=5
        )

        # 2. 构建中间答案：Map步骤
        intermediate_answers = []
        for comm in relevant_communities:
            answer = self.llm.generate(f"""
你是AI分析师，回答基于以下社区报告...

社区报告: {comm['summary']}
查询: {query}

要点:
- 从社区报告中提取与查询相关的事实
- 评估信息的重要性 (1-10)
- 提供引用来源
""")
            intermediate_answers.append(answer)

        # 3. Reduce步骤：汇总最终答案
        final_answer = self.llm.generate(f"""
综合以下中间分析结果，回答用户查询。

查询: {query}

中间分析:
{chr(10).join(f'--- 来源{i+1} ---{a}' for i, a in enumerate(intermediate_answers))}

要求:
- 提供全面的答案
- 标注引用来源
- 指出信息矛盾或不确定性
""")
        return final_answer

    def local_search(self, query: str, entities: List[str] = None) -> str:
        """局部搜索：基于实体关系图"""
        # 1. 实体链接
        if not entities:
            entities = self._extract_query_entities(query)

        # 2. 图谱检索：获取1-2跳邻居
        context = self._get_subgraph_context(entities, hops=2)

        # 3. 向量检索：获取文本上下文
        text_context = self._get_text_context(query)

        # 4. LLM生成
        return self.llm.generate(f"""
基于以下信息回答问题。

图谱上下文:
{context}

文本上下文:
{text_context}

查询: {query}

要求:
- 基于提供的信息回答
- 引用图谱中的具体关系和实体
- 如果不确定，明确说明
""")

    def _get_subgraph_context(self, entities: List[str], hops: int = 2) -> str:
        """获取实体的子图上下文"""
        query = f"""
        MATCH (e:Entity)-[r*1..{hops}]-(neighbor)
        WHERE e.name IN $entities
        RETURN e.name AS entity, type(r[0]) AS relation,
               neighbor.name AS neighbor, neighbor.type AS type
        LIMIT 100
        """
        results = self.graph.run(query, entities=entities)
        context_lines = []
        for row in results:
            context_lines.append(
                f"({row['entity']}) -[{row['relation']}]-> ({row['neighbor']}: {row['type']})"
            )
        return "\n".join(context_lines)
```

## 6. 图算法与应用

### 6.1 核心图算法

```cypher
-- Neo4j GDS图算法示例

-- 1. 中心性分析：谁是最重要的实体？
CALL gds.pageRank.stream('entity_graph')
YIELD nodeId, score
MATCH (e:Entity) WHERE id(e) = nodeId
RETURN e.name, score
ORDER BY score DESC LIMIT 20;

-- 2. 社区检测：哪些实体属于同一群体？
CALL gds.louvain.stream('entity_graph')
YIELD nodeId, communityId
MATCH (e:Entity) WHERE id(e) = nodeId
RETURN communityId, collect(e.name) AS members, count(*) AS size
ORDER BY size DESC LIMIT 10;

-- 3. 相似度：哪些公司最相似？
CALL gds.nodeSimilarity.stream('entity_graph', {topK: 10})
YIELD node1, node2, similarity
MATCH (a:Entity) WHERE id(a) = node1
MATCH (b:Entity) WHERE id(b) = node2
RETURN a.name, b.name, similarity
ORDER BY similarity DESC LIMIT 20;

-- 4. 路径查找：供应链分析
MATCH path = (a:Product {name: "iPhone"})-[r:USES*1..4]-(b:Technology)
RETURN path;
```

### 6.2 规则推理

```cypher
-- 定义推理规则（使用Neo4j APOC）
-- 规则1: 竞争传递性 (如果A与B竞争，B与C竞争，则A可能与C竞争)
CALL apoc.periodic.commit("
  MATCH (a:Company)-[:COMPETES_WITH]->(b:Company)-[:COMPETES_WITH]->(c:Company)
  WHERE NOT (a)-[:COMPETES_WITH]-(c) AND a <> c
  WITH a, c LIMIT $limit
  CREATE (a)-[:COMPETES_WITH {intensity: 'Indirect', derived: true}]->(c)
  RETURN count(*)
", {limit: 1000});

-- 规则2: 技术依赖传递 (如果产品用技术A，技术A依赖技术B，则产品间接依赖技术B)
CALL apoc.periodic.commit("
  MATCH (p:Product)-[:USES_TECHNOLOGY]->(t1:Technology)
  MATCH (t1)-[:DEPENDS_ON]->(t2:Technology)
  WHERE NOT (p)-[:USES_TECHNOLOGY]->(t2)
  WITH p, t2 LIMIT $limit
  CREATE (p)-[:USES_TECHNOLOGY {derived: true}]->(t2)
  RETURN count(*)
", {limit: 1000});
```

```python
class KGMetrics:
    """知识图谱质量评估"""

    @staticmethod
    def completeness(graph) -> float:
        """完备性：实体属性填充率"""
        query = """
        MATCH (n)
        RETURN labels(n)[0] AS label,
               avg(size(keys(n))) * 1.0 / avg(total_props) AS fill_rate
        """
        # total_props: 该实体类型应有的属性总数

    @staticmethod
    def connectivity(graph) -> float:
        """连通性：孤立节点比例"""
        query = """
        MATCH (n)
        WHERE NOT (n)--()
        RETURN count(n) * 1.0 / count { MATCH (m) RETURN count(m) }
        """
        # 孤立节点比例越低越好

    @staticmethod
    def freshness(graph) -> float:
        """新鲜度：最近更新时间"""
        query = """
        MATCH (n)
        RETURN datetime().epochMillis - max(n.updated_at.epochMillis)
               AS max_staleness_ms
        """

    @staticmethod
    def consistency(graph) -> float:
        """一致性：是否存在矛盾关系"""
        # 例如：同一个人不能同时在两家公司担任CEO
        contradictions = graph.run("""
        MATCH (p:Person)-[:CEO_OF]->(c1:Company)
        MATCH (p)-[:CEO_OF]->(c2:Company)
        WHERE c1 <> c2
        RETURN count(p) AS contradictions
        """)
        return contradictions
```

## 总结

知识图谱的核心价值在于 **符号知识的结构化表示 + 显式关系的推理能力**。它和向量数据库不是竞争关系，而是互补：

- **向量数据库**：擅长"找相似"（语义匹配）
- **知识图谱**：擅长"理解关系"（逻辑推理）
- **GraphRAG**：两者结合，兼顾广度和深度

构建知识图谱的工程要点：
1. **本体设计先于数据导入** — 混乱的Schema是技术债
2. **实体消歧是最大难点** — 投入工程资源的优先方向
3. **增量更新优于全量重建** — 知识是有时效性的
4. **质量度量驱动迭代** — 完备性、连通性、一致性
