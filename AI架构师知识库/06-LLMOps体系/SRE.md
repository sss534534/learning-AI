## 1. 传统 SRE vs LLM SRE

SRE 的核心原则（错误预算、SLI/SLO、toil 自动化）在 AI 系统仍然适用，但执行方式有根本差异：

| 维度 | 传统 SRE | LLM SRE |
|------|---------|---------|
| **故障模式** | 二进制（服务 up/down） | 连续谱（回答质量降级、幻觉率上升） |
| **错误预算** | 停机时间（分钟/小时） | 回答质量 + 延迟 + 安全违规的组合指标 |
| **SLO 定义** | 延迟 < 200ms @ p99 | 延迟 + 质量评分 + 安全评分 + 成本预算 |
| **监控信号** | CPU/内存/错误率 | GPU利用率 + KV Cache + Token吞吐 + 质量评分 |
| **故障恢复** | 重启/切换副本 | 降级模型 + 重试策略 + 检查点恢复 |
| **容量规划** | CPU/内存线性模型 | GPU显存 + Token吞吐 + 上下文长度的非线性模型 |
| **toil 定义** | 手动运维操作 | 模型更新、Prompt调优、阈值调参 |
| **变更管理** | 代码/配置变更 | 代码 + 模型版本 + Prompt版本 + 评估结果 |

## 2. LLM 系统的 SLO 设计

### 2.1 分层 SLO 框架

```
业务层 SLO
  ├─ 回答准确率 > 90% (人工抽样 + 自动评估)
  ├─ 幻觉率 < 5% (自动检测)
  └─ 安全违规率 < 0.1%
      ↓
服务层 SLO
  ├─ TTFT (首Token延迟) < 500ms @ p95
  ├─ TPOT (每个Token延迟) < 30ms @ p95
  ├─ 端到端延迟 < 5s @ p99
  └─ 可用性 > 99.9%
      ↓
资源层 SLO
  ├─ GPU 利用率 > 70%
  ├─ KV Cache 命中率 > 60%
  └─ 批处理大小 > 4 req/batch
      ↓
成本层 SLO
  ├─ 每Token成本 < $0.0001
  ├─ 单次推理预算 < $0.01
  └─ GPU 空闲率 < 20%
```

### 2.2 质量 SLO 的挑战

传统 SLO 是客观的（延迟可测量），LLM 质量 SLO 是主观的：

```
问题："回答质量 > 90%" 意味着什么？

测量方式：
  A. 人工评估（黄金标准，但成本高）
  B. LLM-as-Judge（成本低，但有偏差）
  C. 用户反馈（有偏样本，延迟大）
  D. 代理指标（语义相似度，但相关性不足）

答案：四者结合，分层验证
  - 线上：代理指标 + 用户反馈（实时）
  - 线下：LLM-as-Judge + 人工抽样（周期）
  - 校准：定期用人工评估校准 LLM Judge 的偏差
```

## 3. LLM 系统的错误预算

### 3.1 组合错误预算

```python
# LLM 系统的错误预算 = 多个指标的加权组合

def compute_error_budget(
    quality_score: float,      # 回答质量 (0-1)
    safety_score: float,       # 安全通过率 (0-1)  
    latency_slo: float,        # 延迟达标率 (0-1)
    availability: float,       # 可用性 (0-1)
) -> float:
    """
    权重由业务优先级决定。
    知识问答场景：质量权重高，延迟权重低
    实时客服场景：延迟权重高，质量权重中
    """
    weights = {
        "quality": 0.4,     # 质量最重要
        "safety": 0.3,      # 安全其次
        "latency": 0.2,     # 延迟第三
        "availability": 0.1 # 可用性最低（可降级）
    }
    return (
        weights["quality"] * quality_score +
        weights["safety"] * safety_score +
        weights["latency"] * latency_slo +
        weights["availability"] * availability
    )
```

### 3.2 降级决策

```
错误预算剩余 > 50% → 正常运行
错误预算剩余 20-50% → 熔断非核心功能（关闭分析报告、关闭深度推理）
错误预算剩余 5-20% → 降级模型（GPT-4o → GPT-4o-mini，关闭上下文扩展）
错误预算剩余 < 5%  → 只读模式（拒绝非关键请求）
```

## 4. LLM 系统的 toil 自动化

| Toil 来源 | 自动化手段 | 优先级 |
|-----------|-----------|--------|
| 模型更新验证 | 自动评估 pipeline + 回归测试 | P0 |
| Prompt 调优 | 自动 prompt 优化器 + A/B 实验 | P0 |
| 阈值调参 | 自动阈值学习 + 动态调整 | P1 |
| 容量规划 | 自动扩缩容 + 负载预测 | P1 |
| 告警调优 | 告警噪音自动降噪 + 关联分析 | P2 |
