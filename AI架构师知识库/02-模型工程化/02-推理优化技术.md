# 推理优化技术

> 提升大模型服务性能的关键技术

## 1. 推理性能指标

### 1.1 核心指标定义

| 指标 | 英文 | 说明 | 优化目标 |
|------|------|------|----------|
| **首Token延迟** | TTFT (Time To First Token) | 从请求到首字符返回时间 | < 100ms |
| **生成延迟** | TPOT (Time Per Output Token) | 每个token生成时间 | < 50ms |
| **吞吐量** | Throughput | 每秒处理token数 | 最大化 |
| **并发数** | Concurrency | 同时处理的请求数 | 最大化 |

### 1.2 延迟构成分析

```
总延迟 = 网络传输 + 队列等待 + 计算延迟
       ↑              ↑            ↑
   客户端优化    调度优化      算法优化
```

**计算延迟拆解：**
```
Prefill阶段（首token）：
- 处理整个输入序列
- 计算复杂度 O(n²)
- 占TTFT主要部分

Decode阶段（后续token）：
- 逐个生成token
- 利用KV Cache
- 内存带宽瓶颈
```

## 2. 批处理优化

### 2.1 Static Batching（静态批处理）

**原理：** 多个请求合并，同时处理

```
请求1: "你好" → [批处理] → 同时生成
请求2: "Hello" → [批处理] → 同时生成
请求3: "Bonjour" → [批处理] → 同时生成
```

**问题：** 必须等所有请求完成才能返回
- 短请求被长请求拖累
- GPU利用率波动

### 2.2 Continuous Batching（连续批处理）

**原理：** 动态插入新请求，无需等待

```
时间线:
t1: [请求1生成中] 
t2: [请求1继续, 请求2加入]
t3: [请求1完成, 请求2继续, 请求3加入]
```

**核心机制：**
- 每个iteration检查新请求
- 新请求插入batch
- 完成的请求立即返回

**效果：**
- GPU利用率提升2-10倍
- 吞吐量显著提升
- 延迟更稳定

### 2.3 Inflight Batching

**NVIDIA TensorRT-LLM实现：**
- 在CUDA kernel层面调度
- 更细粒度的批处理
- 与Continuous Batching效果类似

## 3. 注意力优化

### 3.1 PagedAttention

**问题：** KV Cache显存管理低效

传统方式：
```
为每个请求预分配最大长度显存
实际使用: [实际长度] + [浪费空间]
```

**PagedAttention方案：**
```
将KV Cache分页管理（类似OS虚拟内存）
- 物理页: 固定大小（如16 tokens）
- 逻辑页表: 映射逻辑位置到物理页
- 动态分配: 按需分配物理页
```

**优势：**
- 显存利用率提升20-40%
- 支持更大batch size
- 支持共享KV Cache（如beam search）

### 3.2 FlashAttention

**问题：** 标准Attention是内存瓶颈

**分析：**
```
HBM（显存）带宽: 1-2 TB/s
SRAM（缓存）带宽: 10-20 TB/s
计算速度: 100+ TFLOPS

标准Attention: 频繁读写HBM → 带宽瓶颈
```

**FlashAttention解决方案：**
```
分块计算 + 在线softmax
1. 将Q/K/V分块加载到SRAM
2. 分块计算注意力分数
3. 在线更新softmax归一化
4. 只输出最终结果到HBM
```

**效果：**
- 减少HBM访问，加速2-4倍
- 更省显存，支持更长序列
- 数值稳定性更好

**版本演进：**
- FlashAttention-1: 基础分块
- FlashAttention-2: 减少non-matmul FLOPs
- FlashAttention-3: Hopper架构优化

### 3.3 Multi-Query Attention (MQA)

**问题：** KV Cache显存占用大

**标准MHA：**
```
每个头有独立的K、V
KV Cache大小 = 2 × num_heads × head_dim × seq_len
```

**MQA方案：**
```
所有头共享同一组K、V
KV Cache大小 = 2 × head_dim × seq_len
```

**效果：** KV Cache减少8-16倍（以32头为例）

**变体 - Grouped-Query Attention (GQA)：**
```
中间方案：几个头共享一组K、V
平衡显存和精度
LLaMA-2、ChatGLM3采用
```

## 4. 解码加速

### 4.1 Speculative Decoding（投机解码）

**核心思想：** 小模型草稿 + 大模型验证

```
流程:
1. 小模型（draft）快速生成K个候选token
2. 大模型（target）并行验证
3. 接受匹配的token，拒绝处重新生成
```

**效果：**
- 加速2-3倍
- 输出分布与原始大模型一致
- 适合长文本生成

**小模型选择：**
- 同系列小模型（如LLaMA-7B + LLaMA-70B）
- 专用draft模型（如Medusa、Lookahead）

### 4.2 Medusa Decoding

**改进版投机解码：**
```
不依赖小模型，而是添加多个解码头
每个头预测未来某个位置的token
并行验证多个候选
```

**优势：**
- 无需额外模型
- 训练成本低
- 加速2-3倍

### 4.3 Lookahead Decoding

**无草稿投机解码：**
```
利用当前上下文中的重复模式
Jacobi迭代方法并行解码
无需辅助模型
```

## 5. 内存优化

### 5.1 KV Cache管理策略

**问题：** 长对话场景KV Cache无限增长

**解决方案：**

| 策略 | 原理 | 效果 |
|------|------|------|
| **滑动窗口** | 只保留最近N个token | 固定显存，可能丢失上下文 |
| **H2O** | 保留Heavy Hitters（重要token） | 保留关键信息 |
| **StreamingLLM** | 保留初始token + 滑动窗口 | 兼顾效率和效果 |
| **压缩缓存** | 定期压缩历史KV | 平衡精度和显存 |

### 5.2 量化KV Cache

**方案：**
- KV Cache INT8量化
- 每token或每channel量化
- 精度损失< 1%

**效果：**
- 显存占用减少50%
- 支持更长上下文
- 带宽需求降低

### 5.3 内存池管理

**vLLM实现：**
```
显存池化管理:
- 预分配大块显存
- 动态分配给KV Cache
- 避免显存碎片
```

## 6. 服务层优化

### 6.1 请求调度

**FCFS（先来先服务）：**
- 简单公平
- 可能导致队头阻塞

**最短作业优先（SJF）：**
- 优先处理短请求
- 降低平均延迟

**多级反馈队列：**
- 动态调整优先级
- 平衡公平性和效率

### 6.2 预填充优化

**Chunked Prefill：**
```
长输入分块处理:
- 避免长请求阻塞短请求
- 与decode阶段交错执行
- 提升整体吞吐量
```

### 6.3 模型并行策略

**张量并行（Tensor Parallelism）：**
```
层内切分，多卡并行
适合: 单节点多GPU
通信: 每layer两次all-reduce
```

**流水线并行（Pipeline Parallelism）：**
```
层间切分，流水执行
适合: 多节点集群
通信: 点对点传输
气泡: 流水线空闲
```

**混合并行：**
```
TP + PP组合
TP: 8卡（单节点）
PP: 跨节点
典型: TP8 + PP4 = 32卡
```

## 7. 框架选型指南

### 7.1 主流推理框架对比

| 框架 | 优势 | 劣势 | 推荐场景 |
|------|------|------|----------|
| **vLLM** | PagedAttention、高吞吐 | 功能相对简单 | 通用LLM服务 |
| **TensorRT-LLM** | NVIDIA极致优化 | 仅NVIDIA、封闭 | 性能敏感生产 |
| **SGLang** | 结构化生成、RadixAttention | 较新、生态小 | 复杂Prompt场景 |
| **TGI** | HuggingFace生态、易用 | 性能一般 | 快速原型 |
| **llama.cpp** | 跨平台、CPU支持 | 功能有限 | 端侧部署 |
| **DeepSpeed** | 微软生态、训练推理一体 | 配置复杂 | 研究训练 |

### 7.2 选型决策树

```
硬件平台?
├── NVIDIA GPU
│   ├── 追求极致性能 → TensorRT-LLM
│   └── 平衡易用性 → vLLM
├── 其他GPU/CPU
│   └── vLLM / llama.cpp
└── 多模态/特殊需求
    └── SGLang / 自研
```

## 8. 性能调优实践

### 8.1 调优参数清单

**批处理参数：**
- `max_num_seqs`: 最大并发序列数
- `max_num_batched_tokens`: 最大批处理token数

**内存参数：**
- `gpu_memory_utilization`: GPU显存利用率目标
- `swap_space`: CPU offload空间

**调度参数：**
- `max_model_len`: 最大序列长度
- `chunked_prefill_token_size`: 预填充分块大小

### 8.2 性能测试方法

**基准测试工具：**
```bash
# vLLM benchmark
python benchmark_throughput.py \
  --model meta-llama/Llama-2-7b \
  --input-len 512 \
  --output-len 128 \
  --num-prompts 1000
```

**关键测试场景：**
1. 固定输入长度，测试吞吐量
2. 固定并发数，测试延迟
3. 混合长度，测试调度效率

### 8.3 监控指标

| 指标 | 说明 | 告警阈值 |
|------|------|----------|
| GPU利用率 | 计算单元利用率 | < 80% |
| 显存占用 | 峰值显存使用 | > 90% |
| 队列长度 | 等待请求数 | > 10 |
| P99延迟 | 99分位延迟 | > 2x均值 |

## 9. 架构师决策清单

### 9.1 优化策略选择

- [ ] 评估延迟要求（实时 vs 离线）
- [ ] 确定吞吐量目标（QPS、Token/s）
- [ ] 分析输入长度分布（短文本 vs 长文本）
- [ ] 选择合适的批处理策略
- [ ] 配置注意力优化（FlashAttention、MQA）
- [ ] 评估投机解码收益
- [ ] 设计KV Cache管理策略

### 9.2 容量规划

```
并发数估算:
并发数 = 目标QPS × 平均生成时间

显存需求估算:
显存 = 模型权重 + KV Cache + 激活值
     ≈ 2×参数量(FP16) + 2×2×层数×维度×序列长度×batch_size
```

### 9.3 常见陷阱

**陷阱1：忽视内存带宽瓶颈**
- decode阶段通常是内存带宽瓶颈
- 单纯增加计算单元效果有限

**陷阱2：批处理过大**
- 大batch增加延迟
- 需平衡吞吐量和延迟

**陷阱3：KV Cache管理不当**
- 长对话场景显存溢出
- 需设计淘汰策略
