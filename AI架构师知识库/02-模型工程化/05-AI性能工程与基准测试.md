# AI性能工程与基准测试

> 从经验调优到数据驱动的AI性能工程体系

## 一、AI性能工程全景

### 1.1 性能工程≠调参

传统做法：OOM了减小batch，慢了换大卡 → **被动灭火**

AI性能工程：数据驱动的系统化方法论：
```
测量 → 建模 → 优化 → 验证 → 监控 → 回归
```

### 1.2 核心性能指标

#### 推理性能

| 指标 | 定义 | 目标 |
|------|------|------|
| TTFT (Time To First Token) | 首token延迟 | < 500ms (交互) |
| TPOT (Time Per Output Token) | 每token生成时间 | < 50ms |
| TBT (Time Between Tokens) | 连续token间隔 | < 30ms |
| Throughput | 每秒处理tokens | 最大化 |
| RPS (Requests Per Second) | 吞吐量(rps) | 最大化 |
| QPS (Queries Per Second) | 完整请求/s | 取决于生成长度 |

#### 训练性能

| 指标 | 定义 | 目标 |
|------|------|------|
| MFU (Model FLOPs Utilization) | 计算效率 | > 50% |
| Step Time | 每步耗时 | 最小化 |
| Tokens/sec/GPU | 吞吐 | 最大化 |
| Scale Efficiency | 扩展效率 | > 90% |
| Time-to-Train | 总训练时间 | 成本约束内最小化 |

### 1.3 延迟建模

```
端到端延迟 = TTFT + TPOT × (生成长度 - 1)

TTFT分解:
  = 网络延迟
  + Tokenizer延迟 (~1ms)
  + Prefill时间 (取决于输入长度 + 模型大小)
  + 调度排队时间
  
TPOT分解:
  = Decode Step时间
  = 模型计算 + KV Cache访问 + 采样
```

### 2.4 性能瓶颈诊断

| 症状 | 可能原因 | 诊断命令 |
|------|---------|---------|
| GPU利用率<80% | CPU瓶颈/IO等待 | 检查DataLoader |
| 显存利用率<50% | 配置过于保守 | 增大batch/max-num-seqs |
| TTFT波动大 | 调度排队 | 检查Continuous Batching配置 |
| TPOT不稳定 | KV Cache碎片 | 检查PagedAttention block_size |
| 吞吐上不去 | 并发不足 | 增大并发/多实例 |

## 三、训练性能基准

### 3.1 训练吞吐模型

```
Tokens/sec/GPU = 
  (Seq_len × Micro_Batch × Accumulation × DP_World) / Step_Time
  
其中 Step_Time = 计算时间 + 通信时间 + IO时间
```

### 3.2 NVIDIA MLPerf Training 基准

| 模型 | GPU | 时间 | TFLOPs/GPU | MFU |
|------|-----|------|-----------|-----|
| GPT-3 175B | 10240×H100 | 3.9min | 312 | 57% |
| Llama 2 70B | 1024×H100 | 3.4min | 285 | 52% |
| Stable Diffusion | 1024×H100 | 2.6min | 298 | 54% |

### 3.3 扩展效率测试

```python
# 扩展效率计算方法
def scale_efficiency(baseline_time_1gpu, time_n_gpu, n):
    ideal_time = baseline_time_1gpu / n
    return ideal_time / time_n_gpu

# 典型期望:
# 8卡: >95%
# 64卡: >90%
# 512卡: >80%
# 4096卡: >65%
```

**扩展效率衰减分析**：
1. 通信开销增大（AllReduce O(log N)）
2. 负载不均衡（某些GPU数据偏多）
3. 同步等待（straggler效应）
4. 全局Batch增大需调整学习率

## 四、GPU利用率优化

### 4.1 GPU饥饿的根因

```
计算时间线示例:

[计算] [空闲] [计算] [空闲] [计算]
        ↑             ↑
    CPU准备数据    AllReduce通信
    
目标: [计 算 计 算 计 算 计 算]
      (通过pipeline重叠消除空闲)
```

### 4.2 优化手段矩阵

| 手段 | 作用 | 典型增益 |
|------|------|---------|
| CUDA Graph | 消除Kernel Launch开销 | +5-15% |
| FlashAttention | 减少显存IO、加速Attention | +20-30% |
| 算子融合 (Fused Kernels) | 减少Kernel调用次数 | +5-10% |
| FP8/BF16训练 | 减少显存和计算 | +30-60% (vs FP32) |
| 通信计算重叠 | 隐藏AllReduce延迟 | +10-20% |
| 梯度累积 | 模拟大batch | 显存受限时 +50%+ |
| 激活重计算 (Gradient Checkpointing) | 时间换空间 | 显存节省 30-50% |

### 4.3 显存管理优化

```
显存分配模型 (训练):
Total = Model_Weights + Gradients + Optimizer_States + Activations

优化策略:
1. Mixed Precision: FP32 → FP16/BF16 weights (50%节省)
2. ZeRO: 分片Optimizer+梯度+参数 (8x+)
3. Activation Checkpointing: 不存中间激活,反向重算
4. CPU/NVMe Offload: 溢出到CPU/SSD
5. 序列长度截断: 限制最大长度
```

## 五、SLO框架与性能承诺

### 5.1 SLO层级设计

```
SLA (Service Level Agreement)
  └── SLO (Service Level Objective)
       └── SLI (Service Level Indicator)

LLM推理 SLO 示例:

Layer 1 - 延迟:
  SLI: P50/P95/P99 TTFT, TPOT
  SLO: P95 TTFT < 1s, P99 TTFT < 3s
  
Layer 2 - 吞吐:
  SLI: Tokens/sec, Requests/sec
  SLO: > 80% 基准吞吐
  
Layer 3 - 可用性:
  SLI: 错误率, 超时率
  SLO: 错误率 < 0.1%, 可用性 > 99.9%
  
Layer 4 - 质量:
  SLI: 输出截断率, 拒绝率
  SLO: 截断率 < 1%
```

### 5.2 错误预算 (Error Budget)

```
错误预算 = 1 - SLO

示例: 99.9% 可用性 = 0.1% 错误预算
  = 43.2分钟/月 允许不可用

用途:
- 新版本发布: 消耗错误预算
- 超过预算 → 冻结发布，优先稳定性
- 预算充足 → 加速迭代
```

### 5.3 燃烧率告警

```
燃烧率 = 实际错误消耗速度 / 预算消耗速度

告警规则:
- 燃烧率 2x持续1h → 低优先级 (page on-call)
- 燃烧率 5x持续30min → 中优先级 (wake on-call)
- 燃烧率 10x持续6min → 高优先级 (紧急响应)

防止: "P99延迟超标5分钟, 但恢复极快" 的误报
```

## 六、负载测试与容量规划

### 6.1 负载模式建模

| 负载类型 | 特征 | 测试策略 |
|---------|------|---------|
| 稳态 | 恒定QPS | 恒定负载测试,找最大吞吐 |
| 周期性 | 工作时间高峰 | 正弦波负载测试 |
| 突发 | 瞬时尖峰 | 阶梯递增, burst测试 |
| 长尾 | 少量但长时间请求 | 长序列 + 短序列混合 |

### 6.2 负载测试脚本

```python
import asyncio
import aiohttp
import time
from dataclasses import dataclass

@dataclass
class LoadTestResult:
    total_requests: int
    success_rate: float
    p50_latency: float
    p95_latency: float
    p99_latency: float
    throughput_rps: float
    avg_tokens_per_second: float

async def load_test(
    endpoint: str,
    prompts: list[str],
    target_rps: float,
    duration_seconds: int = 60
) -> LoadTestResult:
    latencies = []
    tokens_generated = []
    
    async def worker(session):
        for prompt in prompts:
            start = time.time()
            async with session.post(
                f"{endpoint}/v1/completions",
                json={"prompt": prompt, "max_tokens": 200}
            ) as resp:
                data = await resp.json()
            latencies.append(time.time() - start)
            tokens_generated.append(
                data.get("usage", {}).get("completion_tokens", 0)
            )
    
    # Rate limiting control
    interval = 1.0 / target_rps
    async with aiohttp.ClientSession() as session:
        tasks = []
        for _ in range(int(target_rps * duration_seconds)):
            tasks.append(asyncio.create_task(worker(session)))
            await asyncio.sleep(interval)
        await asyncio.gather(*tasks)
    
    latencies.sort()
    return LoadTestResult(
        total_requests=len(latencies),
        success_rate=1.0,
        p50_latency=latencies[len(latencies)//2],
        p95_latency=latencies[int(len(latencies)*0.95)],
        p99_latency=latencies[int(len(latencies)*0.99)],
        throughput_rps=len(latencies)/duration_seconds,
        avg_tokens_per_second=sum(tokens_generated)/duration_seconds
    )
```

### 6.3 容量规划公式

```
所需GPU数量 = 
  (峰值QPS × 平均输入Token × 平均输出Token) 
  / (单GPU吞吐 tokens/s × 目标利用率)

安全系数: 1.5x - 2.0x (应对突发)

示例:
  峰值: 1000 QPS
  输入: 500 tokens, 输出: 200 tokens
  单GPU (4×H100 Llama-70B): ~2000 tokens/s
  
  计算: (1000 × 700) / (2000 × 0.8)
       = 437.5 → 8 GPU
  安全: 8 × 1.5 = 12 GPU
```

## 七、性能回归测试

### 7.1 CI/CD 中的性能门禁

```yaml
# .github/workflows/perf-regression.yml
name: Performance Regression

on:
  pull_request:
    paths:
      - 'model_engine/**'
      - 'serving/**'

jobs:
  perf-test:
    runs-on: [self-hosted, gpu-h100]
    steps:
      - uses: actions/checkout@v4
      - name: Run Performance Benchmarks
        run: |
          python benchmarks/run.py \
            --baseline main \
            --pr ${{ github.head_ref }} \
            --model llama-3-8b \
            --num-prompts 1000
      
      - name: Check Regression
        run: |
          python benchmarks/compare.py \
            --threshold-throughput -5% \
            --threshold-latency +10%
```

### 7.2 性能差异分析

```
性能回归的可能原因:
1. 依赖升级 (transformers, vLLM, torch)
2. 模型权重格式变更 (safetensors → GGUF)
3. 新特性引入 (speculative decoding overhead)
4. 配置变更 (KV cache block_size)
5. 基础设施 (GPU驱动/固件升级)
```

### 7.3 基准数据库

```sql
CREATE TABLE benchmarks (
    id SERIAL PRIMARY KEY,
    timestamp TIMESTAMP DEFAULT NOW(),
    git_commit CHAR(40),
    model_name VARCHAR(100),
    engine_version VARCHAR(50),
    gpu_type VARCHAR(50),
    num_gpus INT,
    throughput_tokens_per_sec FLOAT,
    p50_ttft_ms FLOAT,
    p95_ttft_ms FLOAT,
    p99_ttft_ms FLOAT,
    p50_tpot_ms FLOAT,
    p95_tpot_ms FLOAT,
    mfu_percent FLOAT,
    max_batch_size INT,
    notes TEXT
);

-- 性能趋势查询
SELECT 
    DATE(timestamp) as date,
    AVG(throughput_tokens_per_sec) as avg_throughput,
    PERCENTILE_CONT(0.95) WITHIN GROUP (ORDER BY p95_ttft_ms) as p95_ttft
FROM benchmarks
WHERE model_name = 'llama-3-70b'
  AND timestamp > NOW() - INTERVAL '30 days'
GROUP BY DATE(timestamp)
ORDER BY date;
```

## 八、前沿性能优化技术

### 8.1 投机解码 (Speculative Decoding)

```
原理: 用小模型快速生成候选,大模型并行验证

性能提升: 2-3x 吞吐, 在batch=1时最显著

实现:
  - Medusa: 多头预测
  - Eagle: 特征级预测
  - Lookahead Decoding: Jacobi迭代
```

### 8.2 FP8/FP4 量化推理

| 精度 | 显存节省(vs FP16) | 质量影响 | 硬件支持 |
|------|-------------------|---------|---------|
| FP8 (E4M3/E5M2) | 50% | <0.1% | H100, H200 |
| FP4 (E2M1) | 75% | ~1-2% | B200 (Blackwell) |
| INT8 | 50% | <0.5% | A100, H100 |
| INT4 | 75% | 1-3% | A100, H100 |

> Blackwell B200 是首个支持FP4训练+推理的GPU，9.6 PFLOPS FP4。

### 8.3 动态批处理优化

```
Continuous Batching (vLLM):
- 传统: 同batch请求必须等最慢的完成
- CB: 完成的请求立即退出,新请求立即加入
- 增益: 10x+ 吞吐提升

Iteration-level Scheduling (SGLang):
- RadixAttention: 共享前缀缓存
- 自动KV Cache管理
- 比vLLM高 1.3-2x 吞吐
```
