## 3. 索引流水线

### 3.1 文档处理架构

```
文档上传 → 格式转换 → 文本提取 → 权限标注 → 分块 → 向量化 → 存储
              ↓           ↓           ↓          ↓        ↓
          Unstructured  OCR引擎     ACL检查    递归分割   BGE-M3
          LlamaParse    PaddleOCR   部门/级别   512/50   批量Embedding
```

**关键设计：**

**1. 文档解析（多引擎策略）**
```
文档类型判断:
├── PDF（文本型）→ PyMuPDF → 直接提取
├── PDF（扫描件）→ PaddleOCR → OCR识别
├── Word → python-docx → 直接提取
├── PPT → python-pptx → 提取每页文本+备注
├── Excel → openpyxl → 表格转Markdown
├── HTML → BeautifulSoup → 清洗+提取
└── Wiki → API → 结构化提取
```

**2. 智能分块策略**
```
分块策略选择:
├── 结构化文档（有标题层级）→ 按标题分块
│   保留：标题路径（如"第三章/3.1节"）
├── 表格文档 → 表格整体作为一个chunk
│   转换：Markdown表格格式
├── 代码文档 → 按函数/类分块
│   保留：完整函数签名
└── 普通文本 → 递归字符分块
    chunk_size=512, overlap=50
```

**3. 权限标注**
```python
# 每个chunk携带权限元数据
chunk.metadata = {
    "doc_id": "uuid",
    "source": "财务制度v3.pdf",
    "department": "财务部",        # 所属部门
    "classification": "内部",       # 密级：公开/内部/机密
    "allowed_roles": ["manager", "finance_staff"],
    "effective_date": "2024-01-01",
    "expiry_date": "2025-12-31",
}
```

### 3.2 增量索引

```
触发方式:
├── 手动上传 → 实时索引
├── Wiki更新 → Webhook触发
├── 定时扫描 → 每日凌晨全量diff
└── 数据库变更 → CDC捕获

增量流程:
1. 检测变更文档
2. 删除旧chunk（按doc_id）
3. 解析新文档
4. 分块+向量化
5. 写入Milvus + PostgreSQL
6. 更新索引版本号
```

### 4.2 意图识别与路由

```python
class QueryRouter:
    """查询意图路由"""
    
    def route(self, query: str, user_context: dict):
        intent = self.classify_intent(query)
        
        if intent == "factual":
            # 事实性查询 → 精确检索
            return {
                "strategy": "precise",
                "top_k": 5,
                "rerank": True,
                "llm_model": "qwen-72b"
            }
        elif intent == "analytical":
            # 分析性查询 → 广泛检索+深度推理
            return {
                "strategy": "broad",
                "top_k": 15,
                "rerank": True,
                "llm_model": "qwen-72b"
            }
        elif intent == "conversational":
            # 对话性查询 → 带历史上下文
            return {
                "strategy": "conversational",
                "top_k": 5,
                "rerank": False,
                "llm_model": "qwen-72b",
                "include_history": True
            }
        elif intent == "navigational":
            # 导航性查询 → 直接返回文档链接
            return {
                "strategy": "direct",
                "top_k": 3,
                "rerank": False,
                "llm_model": None  # 不需要LLM
            }
```

### 4.3 权限感知检索

```python
class PermissionAwareRetriever:
    """权限感知检索器"""
    
    def retrieve(self, query: str, user_roles: list, department: str):
        # 构建过滤表达式
        filter_expr = f"""
        (classification == "公开") 
        OR (department == "{department}")
        OR ({self._build_role_filter(user_roles)})
        """
        
        # 向量检索 + 权限过滤
        vector_results = milvus_client.search(
            collection_name="knowledge_base",
            data=[embedding],
            filter=filter_expr,
            limit=20,
            output_fields=["source", "department", "classification"]
        )
        
        # BM25检索 + 权限过滤
        bm25_results = bm25_client.search(
            query=query,
            filter=filter_expr,
            limit=20
        )
        
        # 合并去重
        return self._merge_and_deduplicate(vector_results, bm25_results)
```

## 5. 性能优化

### 5.1 多级缓存

```
查询缓存层级:
L1: 语义缓存（完全相同Query）
    - Redis存储
    - TTL: 1小时
    - 命中率: ~15%

L2: 相似查询缓存（语义相似度>0.95）
    - 向量相似度匹配
    - TTL: 30分钟
    - 命中率: ~10%

L3: 热门文档缓存
    - 高频访问文档的检索结果
    - TTL: 5分钟
    - 命中率: ~5%
```

### 5.2 性能指标

| 指标 | 目标 | 实际 |
|------|------|------|
| P50延迟 | < 500ms | 380ms |
| P99延迟 | < 3s | 2.1s |
| 缓存命中率 | > 25% | 30% |
| 吞吐量 | > 500 QPS | 620 QPS |
| 可用性 | > 99.9% | 99.95% |

### 5.3 扩展性设计

```
水平扩展策略:
├── 查询服务: 无状态，K8s HPA自动扩缩
```

## 9. 经验总结

### 9.1 关键成功因素

1. **分块策略至关重要**：不同文档类型需要不同分块策略，通用方案效果差
2. **权限过滤必须在检索阶段**：不能检索后再过滤，否则结果不足
3. **缓存是性价比最高的优化**：30%缓存命中率可节省大量GPU资源
4. **用户反馈闭环**：点赞/踩数据是优化检索和生成质量的关键信号
5. **监控先行**：上线前必须有完善的监控，否则问题难以定位

### 9.2 踩过的坑

| 问题 | 原因 | 解决方案 |
|------|------|----------|
| 长文档检索效果差 | 分块过大丢失精度 | 按标题层级分块，保留结构 |
| 跨语言检索失败 | Embedding模型不支持 | 切换BGE-M3多语言模型 |
| 并发高时延迟飙升 | Milvus查询节点不足 | 增加查询节点+读写分离 |
| 幻觉问题 | LLM生成不受控 | 强化Prompt约束+添加引用要求 |
| 权限泄露 | 过滤逻辑有漏洞 | 增加独立权限校验层 |

## 深度分析

企业级RAG知识库系统的核心挑战在于将非结构化文档转化为结构化、可检索、带权限的知识资产。本文展示的架构围绕"索引-检索-生成"三阶段展开，其中分块策略的精细设计（按文档类型自适应选择方案）和权限感知检索是两大亮点。相比简单的"Embedding+LLM"模式，该架构通过意图识别实现了查询预处理，将不同类型问题路由到不同的检索策略和模型，显著提升了系统效率和准确率。

从生产运维视角看，多级缓存设计（语义缓存+相似查询缓存+热门文档缓存）是RAG系统性价比最高的优化手段之一。30%的综合缓存命中率意味着近三分之一的查询无需调用LLM推理，这对日均50万次查询的场景意味着显著的GPU成本节约。监控体系的完善程度同样值得关注，从业务指标到质量指标再到基础设施指标的全覆盖，为持续优化提供了数据基础。

该架构的演进路线清晰体现了RAG技术发展趋势。从V1的基础RAG到V2的GraphRAG+多模态+Adaptive RAG，再到V3的智能知识平台，反映出RAG系统正从"检索-生成"的简单组合向知识图谱增强、检索策略自适应、主动推荐等方向演进。对于实践者而言，9.2节中列出的踩坑记录尤其具有参考价值——文档分块粒度、跨语言检索、权限过滤等问题的解决方案直接对应了RAG系统生产化中的关键痛点。
