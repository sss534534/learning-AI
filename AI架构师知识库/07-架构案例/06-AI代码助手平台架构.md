## 1. 项目背景

### 1.1 业务需求

**客户画像：** 大型科技公司，研发团队5000+人

**核心需求：**
- 代码补全与生成（IDE插件集成）
- 代码审查自动化
- 技术文档问答（基于内部代码库）
- 代码迁移辅助（框架升级）
- 代码安全扫描

### 1.2 关键挑战

| 挑战 | 描述 |
|------|------|
| **代码安全** | 源代码不能上传到外部API |
| **长上下文** | 需要理解整个项目/文件上下文 |
| **低延迟** | 代码补全延迟必须<300ms |
| **高并发** | 5000+开发者同时使用 |
| **多语言** | Java/Python/Go/TS等10+语言 |

## 3. 代码补全服务

### 3.1 补全架构

```
开发者输入:
    def calculate_total(items):
        total = 0
        for item in items:
            ↓
┌──────────────────────────────────────┐
│ 1. IDE插件捕获光标位置和上下文        │
│    - 前缀(prefix): 光标前代码        │
│    - 后缀(suffix): 光标后代码        │
│    - 文件路径、语言、项目信息         │
└──────────────┬───────────────────────┘
               ↓
┌──────────────────────────────────────┐
│ 2. 上下文增强                        │
│    - 同文件其他函数签名               │
│    - import语句                      │
│    - 相关类型定义                     │
│    - 项目配置文件                     │
└──────────────┬───────────────────────┘
               ↓
┌──────────────────────────────────────┐
│ 3. FIM (Fill-in-the-Middle) 推理     │
│    模型: CodeLlama-34B               │
│    格式: <PRE>prefix<SUF>suffix<MID> │
│    生成: 补全内容                     │
└──────────────┬───────────────────────┘
               ↓
┌──────────────────────────────────────┐
│ 4. 后处理                           │
│    - 去重（与已有代码对比）           │
│    - 格式校验                        │
│    - 安全检查（不生成危险代码）       │
└──────────────┬───────────────────────┘
               ↓
        IDE显示补全建议（<300ms）
```

### 3.2 延迟优化

**目标：P99延迟 < 300ms**

| 优化手段 | 效果 |
|----------|------|
| **模型量化** | AWQ 4-bit，显存减少75% |
| **KV Cache** | 预分配，减少分配开销 |
| **Continuous Batching** | 多用户请求合并处理 |
| **投机解码** | 小模型草稿+大模型验证 |
| **上下文裁剪** | 只发送相关上下文（<2K tokens） |
| **连接池** | gRPC长连接，减少建连开销 |

**延迟拆解：**
```
总延迟 300ms:
├── 网络传输: 20ms
├── 上下文处理: 30ms
├── Tokenizer: 20ms
├── 模型推理(Prefill): 150ms
├── 模型推理(Decode): 50ms
└── 后处理: 30ms
```

## 5. 代码库RAG

### 5.1 代码索引

```
代码库索引流程:
1. 克隆/监听代码仓库
2. Tree-sitter解析AST
   - 函数/类/接口定义
   - 调用关系
   - 类型依赖
3. 按函数/类级别分块
   - 保留完整函数签名
   - 保留import和类型引用
   - 添加文件路径和语言标签
4. 向量化存储
   - Embedding: 代码专用模型
   - 元数据: 文件路径、语言、作者、最后修改时间
   - 图谱: 调用关系图
```

### 5.2 代码检索

```
查询: "用户认证的实现逻辑"

检索策略:
1. 向量检索: 语义相似度匹配
2. 关键词检索: 函数名/类名匹配
3. 结构检索: 基于AST的调用链追踪
4. 混合排序: 综合三种检索结果

返回:
├── AuthService.java (核心认证类)
│   ├── login() - 登录方法
│   └── validateToken() - Token验证
├── JwtUtil.java (JWT工具类)
│   └── generateToken() - 生成Token
└── SecurityConfig.java (安全配置)
    └── filterChain() - 过滤器链配置
```

## 8. 经验总结

### 8.1 关键成功因素

1. **延迟是生命线**：代码补全超过500ms开发者就会关掉
2. **上下文质量决定效果**：发送给模型的上下文必须精准
3. **私有化部署是刚需**：企业代码安全不可妥协
4. **审查要可操作**：给出具体修改建议而非泛泛而谈
5. **渐进式推广**：先试点团队，再全公司推广

### 8.2 踩过的坑

| 问题 | 原因 | 解决方案 |
|------|------|----------|
| 补全延迟高 | 上下文发送过多 | 限制在2K tokens，只发相关代码 |
| 审查建议不实用 | Prompt不够具体 | 分维度审查+代码示例 |
| 代码索引慢 | 大仓库全量索引耗时 | 增量索引+按需索引 |
| 多语言支持差 | 模型训练数据偏科 | 按语言路由到专用模型 |

## 深度分析

AI代码助手平台的架构设计面临的核心矛盾是"低延迟 vs 高质量"。代码补全场景要求P99延迟低于300ms，但高质量的代码生成往往需要更大的模型和更多的上下文。本文给出的解决方案是多模型分层策略：CodeLlama-34B（AWQ量化）专用于补全场景，通过FIM（Fill-in-the-Middle）推理模式配合高精度上下文裁剪，将P99延迟控制在220ms；而Qwen-72B则用于Chat对话和代码审查等对延迟不敏感的场景。模型量化（AWQ 4-bit）、投机解码、Continuous Batching等优化手段共同构成了延迟保障体系。

代码安全是另一个架构设计的关键约束。全部模型私有化部署、源码不出内网、补全内容过滤（不生成密钥/危险调用）、以及审计日志的全量记录，这些措施对于5000+开发者规模的企业级平台来说是刚性需求。Tree-sitter AST解析结合向量检索的混合检索方案，在保证代码语义理解能力的同时避免了代码数据外传至外部API的风险。

代码审查模块的设计体现了AI辅助的深度。从变更分析到上下文收集，再到多维度审查（Bug检测、安全漏洞、性能问题、最佳实践、测试覆盖），最后生成带具体行号的审查报告，整个过程是"AI增强"而非"AI替代"——开发者的代码审查能力被大幅提升而不是被取代。渐进式推广策略（先试点团队再全公司推广）也是这类企业级AI工具落地的正确路径。
