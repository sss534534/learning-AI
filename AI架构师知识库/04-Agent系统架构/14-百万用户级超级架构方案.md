## 1. 架构 DNA 质变：从单地域到 Cell-based

> [!important] 百万级的核心认知
> 百万用户的致命陷阱是「把 10 万方案 ×10」。单集群到 300 卡以上会遇到：跨 AZ 带宽瓶颈、故障爆炸半径过大、GPU 调度粒度粗糙、单 Region 合规违规。**必须单元化拆分**。

### 1.1 三种架构路径对比

| 方案 | 适用 | 月成本 | 海外延迟 | 合规 | 复杂度 |
|------|------|--------|---------|------|--------|
| **A · 单 Region 超大集群** | 单地域用户 | $1M-$3M | 200-500ms ✗ | 不满足 GDPR ✗ | 低 |
| **B · 多地域 Cell-based** ✓ | 全球化用户 | $1.2M-$3.5M | <80ms ✓ | 数据本地驻留 ✓ | 中高 |
| **C · 多云联邦推理** | 极致成本优化 | $0.8M-$2.5M | 抖动大 | 取决于云厂商 | 极高 |

**本方案选 B**：全球化多地域 + 混合云 + 标准企业合规。

### 1.2 10 万 → 100 万的质变点

| 维度 | 10 万（[[13-十万用户级企业架构方案]], [[15-亿级用户终极架构方案]], [[16-Agent编排层框架生态选型]]） | 100 万（本方案） | 质变本质 |
|------|--------------------------------|----------------|---------|
| Region 数 | 1（多 AZ） | 4-6（多地域） | 数据本地化合规 + 低延迟 |
| GPU 卡数 | 8-32 × H100 | 200-600 × H100 | 单集群调度上限逼近 |
| 部署单元 | 单集群 | Cell（单元化） | 故障隔离 + 弹性裂变 |
| 推理调度 | 单层 SAAR | 双层（全局+本地） | 跨 Cell 溢出 + Spot 套利 |
| 记忆架构 | 单库 | 联邦记忆 | 5-50TB 向量无法单库承载 |
| 成本治理 | 手动 | FinOps 自动化 | GPU 占 75%+，必须自动化 |
| 数据驻留 | 共享池 | 本地驻留 | GDPR/CCPA/DSL 强制 |

### 1.3 Cell-based 核心原则

```
Cell = 1 个 Region + 1 套最小可独立运行的 AgentOS 单元
  · 接入网关 + 编排集群 + 推理池(20-60卡) + 记忆层 + 观测
  · 本地用户 100% 在本 Cell 闭环，不跨区调用
  · 数据本地驻留，满足 GDPR/DSL

Cell 间关系：弱同步
  · 用户身份/计费数据 → CRDT 实时同步（< 500ms）
  · 记忆层 → 默认本地，用户跨境漫游时按需拉取热记忆
  · 全局知识库 → CDN 分发到各 Cell 边缘
```

> [!tip] Cell 裂变规则
> 当任一 Cell 达到 70 卡 GPU 或 30 万用户时，触发裂变：新开 Cell 并渐进迁移 30% 流量。**不扩单 Cell，而是加 Cell**——这是单元化架构的弹性核心。

## 2. 容量基线：百万用户的真实负载画像

### 2.1 用户行为假设

| 维度 | 保守值 | 激进值 | 说明 |
|------|--------|--------|------|
| 注册用户 | 1,000,000 | 1,000,000 | 输入条件 |
| DAU | 300,000（30%） | 500,000（50%） | 企业工具类典型 |
| 人均日会话 | 5 | 10 | Agent 多轮特性 |
| 会话平均轮数 | 8 | 15 | 含工具调用回环 |
| 每轮 LLM 调用 | 1.5 | 3 | 含 Planner/Solver/小模型 |
| 上下文长度 | 4K tokens | 8K tokens | Agent 累积上下文 |
| 输出长度 | 500 tokens | 1000 tokens | |

### 2.2 关键指标推导

```
日推理调用数（保守）= 300,000 × 5 × 8 × 1.5 = 18,000,000 次/日
日推理调用数（激进）= 500,000 × 10 × 15 × 3 = 225,000,000 次/日

峰值 QPS（保守，8h 均匀 + 3x 峰值）= 18,000,000 / 28,800 × 3 ≈ 1,875 QPS
峰值 QPS（激进）= 225,000,000 / 28,800 × 3 ≈ 23,438 QPS

日均 token 吞吐（保守）= 18,000,000 × (4,000 + 500) ≈ 81B tokens/日
日均 token 吞吐（激进）= 225,000,000 × (8,000 + 1,000) ≈ 2,025B tokens/日
```

### 2.3 资源估算（与 10 万方案对比）

| 资源 | 10 万方案 | 100 万方案 | 10x 差异 |
|------|---------|-----------|---------|
| **GPU（推理）** | 8-32 × H100 | **200-600 × H100** | 质变：单集群调度上限逼近 |
| **工作记忆 Redis** | 60-200 GB | **600GB-2TB**（每 Cell 150-500GB） | 线性扩 |
| **向量库** | 50-500 GB | **5-50 TB** | 质变：单库扛不住，必须分片 |
| **情景记忆** | 100GB-1TB/月 | **1-10TB/月**（每 Cell） | 线性扩 |
| **审计日志** | 300GB-3TB/月 | **3-30TB/月** | 质变：跨 Cell 聚合 |
| **对象存储** | 1-10 TB | **10-100 TB** | 线性扩 |
| **带宽** | 500Mbps-5Gbps | **5-50Gbps**（每 Cell 1-12Gbps） | 线性扩 |
| **月成本** | $80K-$300K | **$1.2M-$3.5M** | GPU 占比 65%→75% |

> [!warning] 关键质变
> 峰值万级推理 QPS + 300+ GPU 卡 + 5TB+ 向量规模——任何单 Region / 单组件都扛不住，**必须单元化拆分**。

### 3.3 GSLB 路由策略

```python
class GlobalLoadBalancer:
    async def route(self, request: HttpRequest) -> Cell:
        user_region = self.geoip.lookup(request.client_ip)

        # 1. 优先路由到最近健康 Cell
        cells = self.cells_by_latency(user_region)
        for cell in cells:
            if cell.healthy and cell.capacity_available():
                return cell

        # 2. 最近 Cell 过载 → 溢出到次近 Cell
        for cell in cells:
            if cell.healthy:
                return cell  # 接受排队延迟

        # 3. 全部故障 → 降级页面
        return MaintenanceCell()
```

## 4. 推理层双层调度

### 4.1 为什么需要双层

百万级推理 QPS 下，10 万方案的「单层 SAAR 路由」不够用：

| 场景 | 单层（10万） | 双层（百万） |
|------|------------|------------|
| 正常流量 | 本地路由即可 | 本地路由（99% 请求） |
| Cell 过载 | 排队等待，TTFT 飙升 | 溢出到其他 Cell，无感 |
| Cell 故障 | 全 Cell 用户中断 | 30 秒内切到备 Cell |
| Spot 价格波动 | 无法套利 | 跨 Cell 套利省 20-30% |
| GPU 产能不足 | 被单厂商卡脖子 | 多 Cell 多云分散风险 |

### 4.2 双层调度架构

```
┌─────────────────────────────────────────────────────────────┐
│              全局推理调度器（Global Infer Scheduler）            │
│  · 监控各 Cell 推理负载                                         │
│  · Spot 价格套利（哪个 Cell 的公有云 Spot 便宜就溢出到哪）         │
│  · 跨 Cell 故障转移（Cell-华北宕机 → 流量切到 Cell-新加坡）        │
└────────────────────────┬────────────────────────────────────┘
                         │ 溢出请求（< 10%）
                         ▼
┌─────────────────────────────────────────────────────────────┐
│           Cell 内推理调度（Local Infer Router - SAAR）          │
│  · 会话亲和（prefix cache 命中优先）                             │
│  · 模型亲和（按 model_id 路由到对应池）                           │
│  · 优先级调度（企业版 > 个人版）                                  │
│  · 本地 GPU 池：主干(SGLang H100) + 小模型(vLLM A100)           │
└─────────────────────────────────────────────────────────────┘
```

### 4.3 全局推理调度器实现

```python
class GlobalInferScheduler:
    """跨 Cell 溢出调度 + Spot 价格套利"""

    async def route(self, request: InferRequest) -> Cell:
        # 1. 优先本地 Cell（会话亲和 + 低延迟）
        local_cell = self.cell_of(request.user_id)
        if local_cell.capacity_available():
            return local_cell

        # 2. 本地过载 → 溢出到其他 Cell
        # 优先选 Spot 价格最低的 Cell（成本套利）
        candidates = [c for c in self.cells if c.capacity_available()]
        if candidates:
            return min(candidates, key=lambda c: (
                c.spot_price * 0.7 +    # 成本权重 70%
                c.latency_to(request.user_region) * 0.3  # 延迟权重 30%
            ))

        # 3. 全部过载 → 排队 + 降级
        request.downgrade_model()  # 70B → 14B
        return local_cell  # 本地排队
```

### 4.4 Cell 内推理调度（SAAR）

```python
class CellLocalRouter:
    """Cell 内会话感知路由，复用 10 万方案的 SAAR 逻辑"""

    async def route(self, request: InferRequest) -> Endpoint:
        # 1. 会话亲和：同 session 路由到同实例
        endpoint = await self.session_affinity.get(request.session_id)
        if endpoint and endpoint.healthy:
            return endpoint

        # 2. 前缀感知：KV cache 命中最多的实例
        candidates = await self.prefix_matcher.match(request.prompt_prefix)
        if candidates:
            return max(candidates, key=lambda e: e.cache_hit_ratio)

        # 3. 负载均衡：队列深度 + GPU 利用率
        return await self.least_loaded(self.pool_by_model[request.model_id])
```

## 5. 联邦记忆设计

### 5.1 为什么需要联邦记忆

百万用户的记忆向量规模达 5-50 TB，**单 Qdrant/Milvus 集群扛不住**。需要联邦记忆：每个 Cell 本地存储 + 跨 Cell 按需同步。

| 规模 | 方案 | 瓶颈 |
|------|------|------|
| < 1000 万向量 | 单 Qdrant 集群 | 无 |
| 1000 万-1 亿向量 | Qdrant 集群分片 | 分片路由复杂 |
| > 1 亿向量（百万用户级） | **联邦记忆（每 Cell 本地）** | 跨 Cell 同步 |

### 5.2 联邦记忆架构

```
│  │ Neo4j(关系)  │              │ Neo4j(关系)  │                │
```

### 5.3 记忆分层同步策略

| 记忆类型 | 存储位置 | 同步策略 | 理由 |
|---------|---------|---------|------|
| **工作记忆**（当前会话） | 本地 Redis | 不同步 | 会话在本地 Cell 闭环 |
| **语义记忆**（用户长期） | 本地 Qdrant | 漫游时拉取热记忆 | 数据本地驻留合规 |
| **情景记忆**（事件流） | 本地 TimescaleDB | 不同步 | 事件流本地归档 |
| **关系记忆**（KG） | 本地 Neo4j | 不同步 | 用户关系图本地构建 |
| **全局知识库**（企业共享） | S3 + CDN | CDN 分发到各 Cell | 企业知识全局共享 |

### 5.4 用户跨境漫游的记忆同步

```python
class FederatedMemory:
    async def get_context(self, user_id: str, current_cell: str) -> UserMemory:
        # 1. 优先从本地 Cell 读取
        local = await self.local_store.get(user_id)
        if local and local.is_fresh():
            return local

        # 2. 用户从其他 Cell 漫游过来 → 拉取热记忆
        home_cell = await self.registry.get_home_cell(user_id)
        if home_cell != current_cell:
            # 只拉取最近 7 天热记忆（冷记忆不拉，省带宽）
            hot_memory = await self.cross_cell_fetch(
                user_id, home_cell, days=7
            )
            # 缓存到本地 Cell（TTL 24h）
            await self.local_store.cache(user_id, hot_memory, ttl=86400)
            return hot_memory

        return local or EmptyMemory()

    async def write_back(self, user_id: str, memory: MemoryItem):
        # 写入本地 Cell
        await self.local_store.upsert(user_id, memory)
        # 异步同步到 Home Cell（保证用户回原 Cell 时记忆完整）
        home_cell = await self.registry.get_home_cell(user_id)
        if home_cell != self.current_cell:
            await self.sync_queue.publish({
                'user_id': user_id,
                'home_cell': home_cell,
                'memory': memory
            })
```

### 5.5 联邦记忆的三个坑

> [!danger] 联邦记忆的失败模式
> 1. **记忆冲突**：用户在两个 Cell 同时修改记忆 → 用 Last-Write-Wins + 版本号（vector clock）。关键记忆（如偏好）需合并而非覆盖。
> 2. **同步延迟**：跨 Cell 同步延迟 500ms-2s → 热记忆缓存到本地 Redis，冷记忆不同步。
> 3. **合规遗忘**：用户注销时必须 cascade 清理所有 Cell 的记忆 → 全局遗忘广播（Kafka 全 Cell 消费）。

### 5.6 全局遗忘广播

```python
class GlobalForgettingService:
    """用户注销时全 Cell cascade 清理"""

    async def forget_user(self, user_id: str):
        # 1. 全局广播遗忘指令（Kafka 全 Cell 消费）
        await self.kafka.publish('global.forgetting', {
            'user_id': user_id,
            'ts': datetime.utcnow(),
            'cascade': ['redis', 'qdrant', 'timescaledb', 'neo4j', 's3', 'clickhouse']
        })

        # 2. 各 Cell 消费后本地清理
        # 3. 等待所有 Cell ACK（超时 5 分钟）
        acked = await self.wait_acks(user_id, timeout=300)
        if acked < len(self.cells):
            await self.alert(f"遗忘未完成: {user_id}, ACK {acked}/{len(self.cells)}")

        # 4. 生成合规报告（审计落盘）
        await self.audit_log.record_forgetting(user_id, acked)
```

```python
    async def on_interruption_warning(self, instance: SpotInstance):

        # 1. 标记实例为「不接受新请求」
        instance.drain()
```

```python
class GlobalIAM:

    async def authenticate(self, token: str) -> User:
        # 1. 本地 Cell 验证（JWT 无状态验证）
        user = self.jwt_verify(token)
        if user:

        # 写入 Home Cell
        await self.local_store.create(user)
        # CRDT 同步到所有 Cell（< 500ms）
        await self.crdt_store.sync(f"user:{user.id}", user)
```

```python
class FinOpsController:
    """自动成本优化，无需人工干预"""

    async def hourly_optimize(self):
        # 1. 检查各 Cell Spot 价格
        spot_prices = await self.get_spot_prices()
        cheapest_cell = min(spot_prices, key=lambda x: x.price)
```

```sql
(
```

### 9.1 多层容灾

```
│ Layer 1: Cell 级容灾（Region 故障）                            │

│ · 用户感知：30 秒内重连                                         │
├─────────────────────────────────────────────────────────────┤

│ · 用户感知：无（K8s 自动调度）                                   │
├─────────────────────────────────────────────────────────────┤

│ · 熔断器 + 降级                                                │
│ · 用户感知：质量下降但可用                                      │
├─────────────────────────────────────────────────────────────┤
│ Layer 4: 请求级容灾（单请求失败）                              │
│ · 重试 + Fallback                                              │
│ · 用户感知：无                                                  │
└─────────────────────────────────────────────────────────────┘
```

### 9.2 降级矩阵

| 故障场景 | 降级动作 | 用户感知 | RTO |
|---------|---------|---------|-----|
| **Cell 故障** | GSLB 切换到备 Cell | 30 秒内重连 | 30s |
| **主干模型池全挂** | 切换到小模型（14B） | 质量下降但可用 | 5min |
| **Spot 大规模中断** | 自动迁移到 Reserved | 无感（如果 Reserved 充足） | 2min |
| **Redis 主挂** | Sentinel 切换到副本 | 10 秒内会话重连 | 10s |
| **Qdrant 集群挂** | 降级到 BM25 检索 | 检索质量下降 | 1min |
| **Kafka 拥塞** | 审计日志降级写本地文件 | 无业务影响 | 5min |
| **全局控制平面挂** | 各 Cell 独立运行（降级模式） | 配置无法更新，但业务正常 | - |
| **跨 Cell 网络中断** | 各 Cell 独立运行，记忆不同步 | 漫游用户记忆不完整 | - |

### 9.3 Cell 故障切换流程

```python
class CellFailover:
    """Cell 故障时的自动切换"""

    async def on_cell_unhealthy(self, failed_cell: str):
        # 1. GSLB 标记故障 Cell 为不可用
        await self.gslb.mark_unhealthy(failed_cell)

        # 2. 计算备选 Cell（按延迟排序）
        candidates = self.cells_by_latency(failed_cell.region)
        target = candidates[0]  # 最近的健康 Cell

        # 3. 渐进迁移流量（避免目标 Cell 雪崩）
        for batch in self.batches(failed_cell.users, size=1000):
            await self.gslb.reroute(batch, target)
            await asyncio.sleep(1)  # 每 1 秒迁 1000 用户

        # 4. 通知目标 Cell 预热（拉起额外 GPU）
        await target.scale_up(factor=1.3)

        # 5. 拉取漫游用户的热记忆
        await target.prefetch_hot_memories(failed_cell.users)
```

```python
class GlobalAlertRouter:
    """跨 Cell 告警聚合与路由"""

    async def evaluate(self):
        # 1. 收集各 Cell 告警
        alerts = await self.collect_cell_alerts()

        # 2. 聚合相同根因（避免告警风暴）
        grouped = self.group_by_root_cause(alerts)

        # 3. 按严重度路由
        for group in grouped:
            if group.severity == 'critical':
                if group.affected_cells >= 2:
                    # 多 Cell 故障 → 值班 SRE + 主管
                    await self.notify_oncall(group, escalate=True)
                else:
                    # 单 Cell 故障 → 该 Cell 值班
                    await self.notify_cell_oncall(group)
            else:
                # 非关键 → Slack 通知
                await self.notify_slack(group)
```

```python
class RTBFService:
    """GDPR/CCPA 的 Right To Be Forgotten"""

    async def execute(self, user_id: str, regulation: str):
        # 1. 全局广播遗忘指令
        await self.kafka.publish('global.rtbf', {
            'user_id': user_id,
            'regulation': regulation,  # GDPR / CCPA / DSL
            'ts': datetime.utcnow()
        })

        # 2. 各 Cell cascade 清理
        cascade_steps = [
            'redis_session',       # 会话状态
            'redis_quota',         # 配额计数
            'qdrant_memory',       # 语义记忆
            'timescaledb_events',  # 情景记忆
            'neo4j_relationships', # 关系记忆
            's3_artifacts',        # 用户上传的文件
            'clickhouse_audit',    # 审计日志（匿名化，不删除）
        ]

        # 3. 等待所有 Cell ACK
        acked = await self.wait_all_acks(user_id, timeout=300)

        # 4. 生成合规报告
        report = {
            'user_id': user_id,
            'regulation': regulation,
            'cells_acked': acked,
            'cells_total': len(self.cells),
            'cascade_steps': cascade_steps,
            'completed_at': datetime.utcnow()
        }

        # 5. 审计日志匿名化（保留统计，删除 PII）
        await self.anonymize_audit(user_id)

        return report
```

|---------|---------|---------|

## 13. 深度分析

### 13.1 为什么百万级必须 Cell-based

```
单集群方案在百万级的死法：

1. GPU 调度粒度太粗
   · 300+ 卡在单 K8s 集群，调度器延迟 > 5 秒
   · Pod 调度抖动导致 TTFT P99 飙到 10 秒+

2. 故障爆炸半径过大
   · 单集群故障 = 100 万用户全挂
   · 灾难恢复需要 30+ 分钟

3. 合规违规
   · EU 用户数据存中国 = 违反 GDPR
   · 中国用户数据存海外 = 违反 DSL

4. 跨 AZ 带宽瓶颈
   · 300 卡跨 3 个 AZ，KV cache 同步带宽 > 100Gbps
   · 超出 AZ 间网络上限

Cell-based 方案：
   · 每 Cell 50-70 卡，调度延迟 < 1 秒
   · 单 Cell 故障只影响 20-30 万用户，30 秒切换
   · 数据本地驻留，合规无忧
   · 跨 AZ 流量在 Cell 内部，不跨 Cell
```

### 13.2 混合云 vs 全公有云的决策

```
混合云（本方案）适用：
  · 月 GPU 成本 > $500K（自建折旧回收期 < 3 年）
  · 中国市场占比 > 30%（自建 IDC 满足 DSL）
  · 有机房运维能力
  · 接受前期 CAPEX 投入

全公有云适用：
  · 月 GPU 成本 < $500K（自建不划算）
  · 无中国合规要求
  · 无机房团队
  · 追求 OPEX 模型

百万用户级（月 $1M+ GPU）→ 混合云是唯一经济选择
```

### 13.3 与 10 万方案的映射

| 本方案分层 | 10 万方案（[[13-十万用户级企业架构方案]], [[15-亿级用户终极架构方案]], [[16-Agent编排层框架生态选型]]） | 关键扩展 |
|-----------|--------------------------------------|---------|
| 多地域拓扑 | 单 Region 多 AZ | 从单 Region → 4-6 Cell |
| 推理双层调度 | 单层 SAAR | 从单层 → 全局+本地双层 |
| 联邦记忆 | 单库记忆 | 从单库 → 联邦记忆 + 漫游同步 |
| 混合云 GPU | 单云按需 | 从单云 → 自建+Reserved+Spot |
| 全局控制平面 | 无 | 新增：IAM/计费/模型分发/遗忘广播 |
| FinOps | 手动成本治理 | 从手动 → FinOps 自动化 |
| 容灾 | 多 AZ 降级 | 从多 AZ → 多 Cell + 跨 Cell 故障转移 |

### 13.4 关键决策的批判性审视

> [!abstract] 用「The Fool」批判性思维复盘
> 本方案的关键决策值得用 [[06-生产级框架选型批判性决策指南|../09-Agent框架生态/06-生产级框架选型批判性决策指南]] 的五模式再审视：
>
> - **Expose My Assumptions**：假设 DAU 30%——全球化产品可能因文化差异，某些地区 DAU 仅 10%，导致 Cell 过度配置
> - **Argue the Other Side**：为什么不全部用公有云？因为百万级月 GPU 成本 $1M+，自建折旧 3 年回收，长期省 57%
> - **Find the Failure Modes**：最可能死在"Cell 裂变期的联邦记忆同步"——双 Cell 到四 Cell 的记忆一致性是最大风险
> - **Attack This**：Cell-based 真的比单集群好吗？在 300 卡规模以下，单集群更简单；Cell-based 的控制平面复杂度可能超过收益
> - **Test the Evidence**：成本估算基于 2026 年 H100 价格和 Spot 折扣率，GPU 价格下行可能让全公有云更划算
