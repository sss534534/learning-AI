## 1. MCP 2026-07-28 RC：无状态传输革命

### 1.1 背景：粘性路由的问题

传统 MCP 传输依赖连接建立时协商的状态——包括 protocol version、client capabilities、auth identity、routing tenant。每次 tools/call 调用隐含依赖这些 per-connection 状态。

在生产环境中，这种设计带来以下问题：

| 问题 | 表现 | 影响 |
|------|------|------|
| 负载均衡 | 需要 sticky session 绑定 | 流量分配不均，扩容复杂 |
| 服务器重启 | per-connection 状态丢失 | 正在执行的 agent 任务中断 |
| 蓝绿部署 | 新实例无旧连接状态 | 部署期间 agent 大量重连 |
| 缓存失效 | 每个服务器持有自己的内省缓存 | OAuth token 内省结果不一致 |

### 1.2 Stateless Transport 方案

**PR #2750（2026-05-22）** 是 MCP 规范的重要里程碑。核心变更：tools/call 请求自包含所有字段。

```
Before（粘性路由）:
  Client ———[建立连接时协商状态]———→ Server A
            protocol: 2025-03-26
            capabilities: {streaming: true}
            auth: token_abc
            tenant: org_123
              ↓
          tools/call 依赖连接状态 → 只能由 Server A 处理

After（无状态传输）:
  Client ———→ Server A（或 B 或 C）
            tools/call 请求自包含:
            {
              protocol_version: "2026-07-28",
              capabilities: {streaming: true},
              auth: {bearer: "token_abc"},
              routing: {tenant: "org_123"},
              tool: "search",
              args: {query: "..."}
            }
              ↓
          任何服务器可独立处理该请求
```

**关键变更：**
- 服务器不再假定任何连接级别的状态
- 每个 tools/call 携带服务器所需的所有字段
- 负载均衡可以 round-robin，无需 sticky session

### 1.3 对生产部署的影响

| 领域 | 变化 | 行动项 |
|------|------|--------|
| 负载均衡 | Round-robin 替代 sticky session | 移除 session-affinity 配置 |
| 部署策略 | 蓝绿/滚动升级不中断 agent | 零停机部署成为可能 |
| 缓存架构 | per-connection → 共享存储 | 引入 Redis-equivalent 缓存层 |
| OAuth 内省 | 进程内缓存 → 分布式缓存 | 内省结果共享，TTL 管理 |

### 1.4 迁移路径

```
现有 Server 迁移步骤：
1. 识别所有从连接读取状态的代码路径
   - protocol version check
   - cached OAuth introspection
   - tenant routing decision
2. 改为从请求读取
   - 每个 tools/call 的 header 或 body
3. 移除 per-connection 状态缓存
4. 可选：引入共享缓存层
5. 测试向后兼容性

注意：Legacy SSE 传输仍受支持但已弃用（deprecated）
新实现应使用 Streamable HTTP + Stateless Transport
```

## 2. MCP Authorization 模型

### 2.1 从 OAuth 到 Per-Request 验证

MCP 的授权模型在 2026 年发生根本性转变：

| 版本 | 授权方式 | 特点 |
|------|----------|------|
| 2024-11 | 无内置授权 | 依赖传输层安全 |
| 2025-03-26 | OAuth 2.1 | 连接级授权 |
| **2026-07-28** | **Per-Request Authorization** | 每个请求独立验证 |

**Per-Request Authorization 意味着：**
- 每个 tools/call 携带 bearer token / signed capability / tenant identifier
- 服务器不再在进程内存中持有任何会话状态
- Token 内省缓存位于共享存储（Redis-equivalent）
- 负载均衡器 reshuffle、服务器重启、蓝绿部署不会导致授权丢失

### 2.2 安全边界

```
┌─────────────────────────────────────────────────────────┐
│                 MCP 安全边界                             │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  ┌─────────────────────────────────────────────────┐    │
│  │  传输安全层                                       │    │
│  │  · mTLS / DPoP sender-constrained tokens         │    │
│  │  · Streamable HTTP over HTTPS                    │    │
│  └─────────────────────────────────────────────────┘    │
│                         ↓                               │
│  ┌─────────────────────────────────────────────────┐    │
│  │  请求授权层                                       │    │
│  │  · 每个 tools/call 携带 bearer token             │    │
│  │  · Skill-scoped OAuth（每个工具声明所需 scope）    │    │
│  │  · Agent Card 签名验证（发布者身份确认）           │    │
│  └─────────────────────────────────────────────────┘    │
│                         ↓                               │
│  ┌─────────────────────────────────────────────────┐    │
│  │  工具执行层                                       │    │
│  │  · 最小权限原则：每个工具只访问声明范围内的资源     │    │
│  │  · 沙箱隔离：工具在受限环境中执行                   │    │
│  └─────────────────────────────────────────────────┘    │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

## 3. MCP Apps 与 Tasks 扩展

### 3.1 MCP Apps

MCP Apps 是 2026 年引入的新概念，定义了一组可组合的 MCP Server 集合，作为一个应用单元发布和发现。

**App 的结构：**
```
mcp-app.json
{
  "name": "data-analysis-app",
  "version": "1.0.0",
  "servers": [
    "mcp://database-server",
    "mcp://visualization-server",
    "mcp://report-server"
  ],
  "capabilities": {
    "query": ["database-server.query"],
    "chart": ["visualization-server.create_chart"],
    "report": ["database-server.query", "report-server.generate"]
  }
}
```

### 3.2 MCP Tasks

MCP Tasks 提供了跨多个 Server 的有状态工作流定义能力。

**Task vs A2A 的边界：**
- MCP Tasks = 工具级别的编排（单一 Agent 内）
- A2A = Agent 级别的协作（跨 Agent）

## 4. MCP 在 Agentic AI Foundation 下的治理

### 4.1 AAIF 成立

**2025 年 12 月**，Linux Foundation 宣布成立 **Agentic AI Foundation（AAIF）**，这是一个定向基金（Directed Fund），旨在标准化和治理 AI Agent 生态的基础设施。

| 细节 | 内容 |
|------|------|
| 成立时间 | 2025 年 12 月 |
| 治理主体 | Linux Foundation LF AI & Data |
| 创始成员 | OpenAI、Anthropic、Google、Microsoft、AWS、Block |
| 截至 2026-04 | 170+ 成员组织 |

**入驻项目：**
- **MCP**（Anthropic 捐赠）— Agent-to-Tool 协议
- **Goose**（Block 捐赠）— 开源 Agent 运行时
- **AGENTS.md**（OpenAI 捐赠）— Agent 仓库地图规范

### 4.2 行业意义

```
Protocol War 的终结
────────────────
2024: 各厂商各自为政
  · Anthropic → MCP
  · Google → A2A
  · IBM → ACP
  · OpenAI → 无公开协议

2025: 整合开始
  · MCP 被广泛采纳成为事实标准
  · A2A 捐赠给 Linux Foundation
  · ACP 与 A2A 合并

2026: AAIF 统一治理
  · MCP 和 A2A 在同一基金会下协同演进
  · 联合规范制定中
  · 开源生态 → 标准化基础设施
```

## 5. MCP + A2A 联合规范

### 5.1 联合规范目标

2026 年下半年预计发布 MCP + A2A 联合规范，形式化 tool 层与 agent 层的交接协议。

**核心目标：**
- 明确 MCP 和 A2A 的边界
- 定义两者之间的标准交接接口
- 统一的安全和授权模型

### 5.2 参考架构

```
                    ┌─────────────────────┐
                    │     Agent A         │
                    │  (Orchestrator)     │
                    └──────┬──────────────┘
                           │ A2A 协议
                    ┌──────▼──────────────┐
                    │     Agent B         │
                    │  (Specialist)       │
                    └──────┬──────────────┘
                           │ MCP 协议
              ┌────────────┼────────────┐
              │            │            │
              ▼            ▼            ▼
        ┌──────────┐ ┌──────────┐ ┌──────────┐
        │ 数据库    │ │ 搜索 API │ │ 文件系统  │
        │ MCP Svr  │ │ MCP Svr  │ │ MCP Svr  │
        └──────────┘ └──────────┘ └──────────┘

图解：
  · A2A = Agent ↔ Agent 协作（横向）
  · MCP = Agent ↔ Tool 执行（纵向）
  · 联合规范 = 标准化两者的交接
```
