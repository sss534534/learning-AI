## 1. 评审框架概述

### 1.1 为什么需要专门的评审方法论？

Agent 系统不同于传统 Web 应用或微服务，它有独特的架构关注点：

| 传统应用 | Agent 系统 |
|---------|-----------|
| 确定性逻辑 | 概率性推理 |
| 请求-响应 | 多步循环（观察-思考-行动） |
| 代码正确性 | 工具选择准确率 |
| 数据库一致性 | 记忆持久化与衰减 |
| API 限流 | LLM Token 预算管理 |
| 日志审计 | 思维链可解释性 |

因此，评审 Agent 架构需要一套专门的框架。

### 1.2 评审目标

一次完整的 Agent 架构评审应回答三个问题：

1. **当前状态**：系统在多大程度上达到了生产级标准？
2. **关键差距**：最紧急、影响最大的问题是什么？
3. **改进路径**：如何分阶段达到目标水平？

### 2.1 Agent 核心循环

**评估要点**：

| 检查项 | 说明 | 权重 |
|--------|------|------|
| 循环模式 | ReAct / O-T-A-V / Plan-Execute？是否适配场景？ | 高 |
| 状态管理 | 执行状态是否可持久化？支持断点续传？ | 高 |
| 步数控制 | 是否有最大步数限制？防止死循环？ | 中 |
| 流式输出 | 推理过程是否对用户可见（SSE）？ | 中 |
| 解析鲁棒性 | LLM 输出解析失败时如何处理？有重试/修正机制？ | 中 |
| 模型参数化 | 模型名/参数是否可配置，而非硬编码？ | 高 |

**常见问题**：模型名硬编码、流式输出缺失、解析失败静默 fallback。

### 2.2 路由与意图识别

**评估要点**：

| 检查项 | 说明 | 权重 |
|--------|------|------|
| 路由策略 | 关键词→规则→LLM 多级路由是否合理？ | 高 |
| 快速通道 | 简单查询是否有快捷路径（跳过 LLM）？ | 中 |
| 配置化程度 | 路由规则是否可配置（非硬编码）？ | 中 |
| 失败处理 | 路由失败时的降级策略是什么？ | 高 |
| 可观测性 | 路由决策是否被记录和统计？ | 中 |

**常见问题**：路由词表硬编码、路由失败静默降级无告警、无 A/B 统计。

### 2.3 工具管理系统

**评估要点**：

| 检查项 | 说明 | 权重 |
|--------|------|------|
| 注册机制 | 工具如何注册？是否有别名/模糊匹配？ | 中 |
| 工具筛选 | 大量工具时如何缩小候选集？ | 高 |
| 工具分类 | 核心工具/通用工具是否分类管理？ | 中 |
| 选择验证 | 工具选择后是否有置信度验证？ | 中 |
| 双轨问题 | 是否存在多套独立的工具体系？ | 高 |

**常见问题**：双轨工具体系并存、工具数量爆炸未分类、过滤依赖描述质量。

### 2.4 记忆系统

**评估要点**：

| 检查项 | 说明 | 权重 |
|--------|------|------|
| 分层设计 | 工作记忆/短期/长期是否分层？ | 中 |
| 持久化 | 各层记忆是否持久化？（重启不丢失） | **严重** |
| Token 管理 | 短期记忆是否有 Token 窗口截断？ | **严重** |
| 衰减机制 | 是否有时间衰减/重要性加权？ | 中 |
| 跨会话 | 跨会话知识是否能传递？ | 高 |

**常见问题**：全部记忆在内存、无 Token 截断、无跨会话能力。

### 2.5 工作流引擎

**评估要点**：

| 检查项 | 说明 | 权重 |
|--------|------|------|
| DAG 支持 | 是否支持依赖关系 + 拓扑排序？ | 高 |
| 并行执行 | 无依赖的步骤是否并行？ | 中 |
| 条件/分支 | 支持哪些条件表达式？ | 中 |
| 审批流 | 高风险步骤是否支持人类审批？ | 高 |
| 恢复机制 | 审批恢复是否从断点继续（非从头）？ | 高 |
| 重试策略 | 步骤失败是否支持重试？ | 中 |

**常见问题**：审批恢复从头执行、条件表达式能力弱、无重试策略。

### 2.6 安全与权限

**评估要点**：

| 检查项 | 说明 | 权重 |
|--------|------|------|
| 认证集成 | 是否与真实认证系统（JWT/OAuth2）集成？ | **严重** |
| RBAC 模型 | 角色/权限是否可动态配置？ | 高 |
| 工具风控 | 高风险工具是否需要二次确认？ | 高 |
| API 鉴权 | Controller 层是否有安全注解？ | **严重** |
| 持久化 | 安全配置是否持久化（非内存）？ | **严重** |

**常见问题**：全内存实现、无真实认证、Controller 无鉴权。

### 2.7 可观测性

**评估要点**：

| 检查项 | 说明 | 权重 |
|--------|------|------|
| 执行追踪 | Agent 每步是否可追踪？ | 高 |
| 审计日志 | 审计日志是否持久化？ | **严重** |
| Metrics | 是否暴露 Prometheus/Micrometer 指标？ | 高 |
| LLM 监控 | Token 用量/延迟/成本是否监控？ | 高 |
| 告警 | 错误率/延迟异常是否有告警？ | 中 |
| Health Check | 是否有 /actuator/health？ | 中 |
| Trace ID | 全链路是否有 Trace ID 传播？ | 中 |

**常见问题**：审计日志在内存、无 LLM 调用监控、无 Metrics。

### 2.8 容错与弹性

**评估要点**：

| 检查项 | 说明 | 权重 |
|--------|------|------|
| 整体超时 | Agent 循环是否有总超时？ | 高 |
| 熔断 | LLM 调用是否有 Circuit Breaker？ | 高 |
| 限流 | API 层是否有 Rate Limiter？ | 中 |
| 线程池 | 线程池是否有界？队列是否可控？ | 中 |
| 降级 | 工具调用失败是否有 fallback？ | 中 |

**常见问题**：无整体超时、无熔断、线程池无界。

### 2.9 多模型/多模态

**评估要点**：

| 检查项 | 说明 | 权重 |
|--------|------|------|
| 模型类型 | 支持哪些模型类型？ | 中 |
| 配置化 | 模型配置是否可动态切换？ | 中 |
| 健康检查 | 模型是否有可用性检查？ | 中 |
| Fallback 链 | 主模型失败是否自动切换备选？ | 中 |
| 缓存策略 | 模型实例缓存是否合理（过期/刷新）？ | 低 |

**常见问题**：缓存永不过期、无 fallback 链。

### 2.10 测试覆盖

**评估要点**：

| 检查项 | 说明 | 权重 |
|--------|------|------|
| 单元测试 | 核心逻辑是否有单元测试？ | **严重** |
| 工具选择测试 | 是否有回归测试集？ | 高 |
| 集成测试 | 是否有端到端 Agent 测试？ | 高 |
| 评估框架 | 是否有类似 LangSmith 的评估体系？ | 中 |
| Prompt 回归 | Prompt 变更是否有回归测试？ | 中 |

**常见问题**：零测试覆盖——这是最容易被忽视但影响最大的问题。

## 3. 评分标准与等级定义

### 3.1 等级定义

| 等级 | 分数 | 含义 | 典型特征 |
|------|------|------|---------|
| ★★★★★ | 90-100 | 行业顶尖 | 全部维度达到生产级，有前沿探索 |
| ★★★★☆ | 75-89 | 生产可用 | 核心维度达标，个别维度有短板 |
| ★★★☆☆ | 60-74 | 演示级 | 功能可用，但生产化严重不足 |
| ★★☆☆☆ | 40-59 | 原型级 | 核心逻辑存在，工程化缺失 |
| ★☆☆☆☆ | 0-39 | 概念级 | 仅有框架，大量功能待实现 |

### 3.2 商用临界线

**85 分** 是生产系统的最低可接受分数。低于此线的系统应优先完成 P0/P1 加固后再上线。

### 3.3 评分计算

```
总分 = Σ(维度得分 × 维度权重)

维度权重：
- 核心能力层（3个维度）: 各 12% = 36%
- 基础设施层（3个维度）: 各 12% = 36%
- 质量保障层（4个维度）: 各  7% = 28%
```

**严重检查项（标「严重」的项）未通过 → 该维度最高 3 分（满分 5）。**

## 4. 评审流程

### 标准评审五步法

```
步骤1: 代码结构扫描
  ↓   了解项目结构、识别 Agent 子系统、统计文件数量
步骤2: 核心路径追踪
  ↓   从 Controller → Agent → Tool Call 跟踪完整调用链
步骤3: 逐维度评审
  ↓   按十大维度逐一检查代码实现
步骤4: 问题分级
  ↓   P0(阻塞上线) / P1(上线前修复) / P2(持续优化)
步骤5: 路线图输出
      分阶段改进计划 + 优先级排序
```

### 问题分级标准

| 级别 | 定义 | 示例 |
|------|------|------|
| **P0** | 阻塞上线，必须在首次发布前修复 | 审计日志不持久化、无认证集成 |
| **P1** | 上线前应修复，短期影响质量 | 无熔断、缺少 Token 管理 |
| **P2** | 持续迭代中优化 | 表达式引擎升级、A/B 测试框架 |

## 5. 实战评审案例：platform-ai-ws

### 5.1 项目概况

- **项目**：HIP 网管系统 AI Agent 模块（Spring Boot 3 + Spring AI 1.0.0 GA）
- **规模**：~180 个 Java 源文件
- **架构**：Claude-style O-T-A-V 循环 + YAML 驱动工作流 + 三层混合路由

### 5.2 评审结果

| 维度 | 评分 | 关键发现 |
|------|------|---------|
| Agent 核心循环 | ★★★★☆ | O-T-A-V 设计优秀，但模型名硬编码 |
| 路由与意图识别 | ★★★★☆ | 三层路由合理，但词表硬编码 |
| 工具管理系统 | ★★★★☆ | 从 4062 工具筛选到 50 核心工具的设计精巧 |
| 记忆系统 | ★★★☆☆ | 分层设计好，但工作记忆+长期记忆不持久化 |
| 工作流引擎 | ★★★★☆ | YAML 驱动 DAG 优秀，审批恢复有问题 |
| 安全与权限 | ★★★☆☆ | RBAC 模型存在，但全内存+未集成真实认证 |
| 可观测性 | ★★☆☆☆ | 有 ExecutionTracer 但结果不持久化 |
| 容错与弹性 | ★★☆☆☆ | 仅有基础重试，无熔断/限流/超时 |
| 多模型/多模态 | ★★★★☆ | 支持 5 种模型，配置化程度高 |
| 测试覆盖 | ★☆☆☆☆ | 5 个测试文件全部是 contextLoads() 桩 |

**综合评分：65/100**

### 5.3 8 个 P0 关键问题

1. 全内存状态 — 6 个核心组件无持久化
2. 安全未集成真实认证 — 无 Spring Security/JWT
3. 审计日志仅内存队列 — 最多 10000 条，重启丢失
4. 双路径 Agent 入口 — SSE 流式 vs 同步执行不一致
5. 模型名硬编码 — `"Qwen3-30B-A3B"` 写死在 think() 方法
6. LLM 调用无监控 — 无 Token 计数/成本追踪
7. 测试覆盖为零 — 5 个桩测试
8. 短期记忆无 Token 截断 — 长对话可能 context 溢出

## 6. 常见反模式与陷阱

### 反模式 1：全内存状态管理

```
症状: LayeredMemory、SecurityService、AuditService 全部是 ConcurrentHashMap
后果: 服务重启 → 所有运行时状态丢失
修复: 关键状态（用户偏好、审计日志、安全配置）必须持久化到 MySQL/Redis
```

### 反模式 2：双轨 Agent 执行

```
症状: ChatService (Spring AI ToolCalling + SSE) 和 ClaudeOrchestrator (同步 O-T-A-V) 并存
后果: 用户体验不一致，维护两套代码
修复: 统一 Agent 入口，O-T-A-V 改造为 SSE 流式输出
```

### 反模式 3：Prompt 硬编码

```
症状: SYSTEM_PROMPT 是 100 行 Java 字符串常量
后果: 改一个词要重新编译部署
修复: Prompt 模板化 → 外部配置 → 版本管理 → A/B 测试
```

### 反模式 4：LLM 输出解析脆弱

```
症状: 用 `{` 位置截取 JSON，多一个换行就失败
后果: 解析失败率高，降级为放弃任务
修复: JSON 修复库 + 结构化输出（JSON mode）+ 解析失败重试
```

### 反模式 5：配置与代码耦合

```
症状: 路由关键词、工具别名、核心工具列表全部硬编码在 Java 中
后果: 加一个关键词要改代码
修复: 配置文件/YAML/数据库驱动，支持热更新
```

## 深度分析

Agent 架构评审方法论为评估生产级 Agent 系统提供了系统化的框架。本文提出的十大评审维度（核心循环、路由意图、工具管理、记忆系统、工作流引擎、安全权限、可观测性、容错弹性、多模型、测试覆盖）覆盖了从核心能力到质量保障的全生命周期。65 分的 platform-ai-ws 实战案例让评审方法论不再停留在理论层面，而是有了具象的参照。

评审的核心价值在于帮助团队回答三个关键问题：当前系统处于什么水平、最大的差距在哪、如何分阶段改进。尤其是 P0/P1/P2 的问题分级方法，让团队可以聚焦最重要的问题，避免在低价值优化上浪费时间。反模式章节中总结的全内存状态、双轨执行等陷阱，是每一个 Agent 团队都可能踩的坑。

本文与成熟度模型紧密关联——评审结果是成熟度评估的输入，而成熟度模型又为评审后的改进提供了路线图。建议团队将评审作为常态化机制，每季度进行一次架构健康检查。

- [ ] 模型名/参数是否可配置非硬编码？
- [ ] LLM 输出解析是否有容错和重试机制？
- [ ] 路由策略是否有快速通道跳过 LLM？
- [ ] 工具注册是否统一无多套体系？
- [ ] 所有记忆层是否持久化重启不丢失？
- [ ] 审计日志是否持久化？
- [ ] LLM 调用是否有 Token/延迟/成本监控？
- [ ] Agent 循环是否有整体超时和熔断？
- [ ] 核心逻辑是否有单元测试覆盖？
