## 1. 容量基线：10 万用户的真实负载画像

> [!important] 容量估算先于架构
> 没有数字的架构图都是 PPT。10 万用户的瓶颈不在"用户数"，而在**并发会话数 × 每会话推理调用数 × 单次 token 成本**。

### 1.1 用户行为假设

| 维度 | 保守值 | 激进值 | 说明 |
|------|--------|--------|------|
| 注册用户 | 100,000 | 100,000 | 输入条件 |
| DAU | 30,000（30%） | 50,000（50%） | 企业工具类典型 20-40% |
| 人均日会话 | 5 | 10 | Agent 场景多轮特性 |
| 会话平均轮数 | 8 | 15 | 含工具调用回环 |
| 每轮 LLM 调用 | 1.5 | 3 | 含 Planner/Solver/工具选择小模型 |
| 上下文长度 | 4K tokens | 8K tokens | Agent 累积上下文 |
| 输出长度 | 500 tokens | 1000 tokens | |

### 1.2 关键指标推导

```
日推理调用数（保守）= 30,000 × 5 × 8 × 1.5 = 1,800,000 次/日
日推理调用数（激进）= 50,000 × 10 × 15 × 3 = 22,500,000 次/日

峰值 QPS（保守，8 小时均匀 + 3x 峰值）= 1,800,000 / 28,800 × 3 ≈ 188 QPS
峰值 QPS（激进）= 22,500,000 / 28,800 × 3 ≈ 2,344 QPS

日均 token 吞吐（保守）= 1,800,000 × (4,000 + 500) ≈ 8.1B tokens/日
日均 token 吞吐（激进）= 22,500,000 × (8,000 + 1,000) ≈ 202B tokens/日
```

### 1.3 资源估算

| 资源 | 保守场景 | 激进场景 | 估算依据 |
|------|---------|---------|---------|
| **GPU（推理）** | 8 × H100 | 32 × H100 | 单卡 SGLang 吞吐 ~200 tokens/s（7B 模型，Agent 负载），主干 70B 模型单卡 ~50 tokens/s |
| **工作记忆 Redis** | 60 GB | 200 GB | 30K 活跃会话 × 1MB 状态 + 缓存 30% |
| **向量库** | 50 GB | 500 GB | 用户记忆 10 万 × 100 条 + 企业知识库 10-100 GB |
| **情景记忆（TimescaleDB）** | 100 GB/月 | 1 TB/月 | 1.8M-22.5M 事件/日 × 1KB |
| **审计日志（ClickHouse）** | 300 GB/月 | 3 TB/月 | 全链路 trace + 工具调用 + 模型版本 |
| **对象存储（S3）** | 1 TB | 10 TB | 上传文档、生成产物、模型快照 |
| **带宽** | 500 Mbps | 5 Gbps | 出口流量为主 |

> [!warning] GPU 是核心瓶颈
> 10 万用户的成本结构中，**GPU 占 60-75%**，存储和带宽各占 10-15%。架构设计的核心目标是**提高 GPU 利用率**，而非堆组件。

### 2.1 拓扑设计原则

| 原则 | 实现 | 价值 |
|------|------|------|
| **无状态计算 + 有状态 Sidecar** | Agent 编排服务无状态，会话状态外置到 Redis | 水平扩展零障碍，副本数随 QPS 线性扩 |
| **读写分离** | 向量库 Qdrant 读多写少 → 读副本独立扩 | 检索 QPS 与写入解耦 |
| **冷热分层** | 情景记忆热数据 7 天 Redis，冷数据归档 ClickHouse | 降低时序库压力 |
| **协议化边界** | MCP（工具）/ OpenTelemetry（trace）/ OpenAI API（推理） | 内部组件可替换，无供应商锁定 |
| **多 AZ 部署** | 推理集群、记忆层、编排层跨 2-3 个 AZ | 单 AZ 故障自动切换 |

## 3. 接入层：多租户网关与流量治理

### 3.1 三层网关架构

```
Internet
   │
   ▼
[Layer 1: WAF + DDoS] ─── Cloudflare / 阿里云盾
   · OWASP 规则集
   · Bot 识别（LLM 流量易被爬）
   · 速率限制（IP 维度）
   │
   ▼
[Layer 2: API Gateway] ─── Kong / APISIX（K8s Ingress）
   · JWT/OAuth2 校验
   · 多租户路由（tenant_id → 命名空间）
   · 配额执行（Redis Lua 原子扣减）
   · 请求染色（trace_id 注入）
   │
   ▼
[Layer 3: Service Mesh] ─── Istio / Linkerd
   · mTLS 服务间通信
   · 熔断器（每个下游服务独立配置）
   · 重试预算（避免雪崩）
   · 金丝雀路由（按 tenant_id 灰度）
```

### 3.2 多租户路由策略

```yaml
# APISIX 路由配置示例
routes:
  - uri: /v1/agents/:agent_id/chat
    upstream:
      type: roundrobin
      nodes:
        agent-编排-v2: 90    # 稳定版
        agent-编排-v3: 10    # 金丝雀版
    plugins:
      jwt-auth: {}
      limit-req:
        key: tenant_id
        rate: 100            # 每租户 100 QPS
        burst: 50
      proxy-rewrite:
        headers:
          set:
            X-Tenant-ID: "$jwt_payload.tenant_id"
            X-Trace-ID: "$request_id"
```

### 3.3 坑

> [!danger] 多租户隔离的三种失败模式
> 1. **配额绕过**：JWT 校验失败但下游服务不校验 tenant_id → 跨租户数据泄露。**对策**：在 Service Mesh 层强制校验 `X-Tenant-ID` 与 JWT 一致。
> 2. ** noisy neighbor**：单租户突发流量挤占共享推理集群 → 其他租户 TTFT 飙升。**对策**：推理层按租户等级分配 GPU 池（企业版独占池 + 共享池）。
> 3. **限流粒度错误**：只按 IP 限流，企业用户走 NAT 出口共用 IP → 误杀。**对策**：按 `tenant_id + user_id` 双维度限流。

## 4. 编排层：Agent 运行时与会话管理

### 4.1 双集群分离

```
┌─────────────────────────────┐    ┌─────────────────────────────┐
│  会话服务集群（轻量）            │    │  Agent 编排集群（重）           │
│  · HTTP/WebSocket 长连接       │    │  · LangGraph StateGraph 执行  │
│  · 会话状态读写（Redis）        │    │  · ToT/ReAct 推理循环          │
│  · 流式响应聚合（SSE）          │    │  · 工具调用编排（MCP）          │
│  · 20-50 副本，CPU 节点         │    │  · 20-50 副本，CPU + 内存     │
└─────────────────────────────┘    └─────────────────────────────┘
```

> [!tip] 为什么分离
> 会话服务是 IO 密集（长连接 + Redis 读写），编排服务是 CPU 密集（图状态机 + JSON 解析 + prompt 拼装）。混部会导致长连接占用 CPU 时间片，影响编排吞吐。

### 4.2 会话状态外置

```python
# 会话状态全部外置到 Redis，编排服务无状态
class SessionStore:
    async def get_context(self, session_id: str) -> SessionContext:
        # Redis Hash: session:{id} → {tenant_id, user_id, agent_id, history_ref, budget}
        return await redis.hgetall(f"session:{session_id}")

    async def checkpoint(self, session_id: str, state: GraphState):
        # LangGraph checkpointer → Redis（热）+ S3（冷，>24h）
        await redis.setex(f"ckpt:{session_id}", 86400, state.json())
        if state.depth > 5:  # 深度推理状态归档
            await s3.put(f"checkpoints/{session_id}/{state.ts}.json", state.json())
```

### 4.3 编排框架落地

| 场景 | 框架 | 理由 |
|------|------|------|
| **主干 Agent**（多轮 + 工具 + 人在回路） | LangGraph | StateGraph + checkpointer + interrupt_before，10 万用户级别的状态管理刚需 |
| **多 Agent 协作**（角色分工） | AutoGen / MAF | 角色扮演 + GroupChat，跨 Agent 通信 |
| **轻量任务 Agent**（FAQ / 路由） | CrewAI | 启动快，无状态，适合高并发简单场景 |

### 5.2 为什么主干用 SGLang

10 万用户场景下，Agent 多轮对话的 **prompt 结构高度重叠**：

```
所有用户的 system_prompt 相同（~2K tokens）
所有用户的 tool_scaffolding 相同（~1K tokens）
单用户多轮历史累积（~1-4K tokens）

SGLang RadixAttention 自动共享前 3K tokens 的 KV 块
→ 显存占用降低 60%+
→ 吞吐提升 2-5x（vs vLLM 无前缀缓存）
```

### 5.3 路由策略

```python
# SAAR 会话感知路由核心逻辑
class SAARRouter:
    async def route(self, request: InferRequest) -> Endpoint:
        # 1. 会话亲和：同 session_id 路由到同实例，命中 prefix cache
        endpoint = await self.session_affinity.get(request.session_id)
        if endpoint and endpoint.healthy:
            return endpoint

        # 2. 前缀感知：选择 KV cache 命中最多的实例
        candidates = await self.prefix_matcher.match(request.prompt_prefix)
        if candidates:
            return max(candidates, key=lambda e: e.cache_hit_ratio)

        # 3. 负载均衡：按队列深度 + GPU 利用率
        return await self.least_loaded(self.pool_by_model[request.model_id])
```

### 6.2 多租户隔离（存储层硬隔离）

```python
# Qdrant 多租户：用 payload 字段 + partition key
from qdrant_client import QdrantClient

client = QdrantClient(host="qdrant-cluster", port=6333)

# 写入时强制打 tenant 标签
def upsert_memory(tenant_id: str, user_id: str, content: str, embedding: list):
    client.upsert(
        collection_name="user_memory",
        points=[{
            "id": uuid4(),
            "vector": embedding,
            "payload": {
                "tenant_id": tenant_id,   # 强制
                "user_id": user_id,
                "content": content,
                "ts": datetime.utcnow()
            }
        }]
    )

# 检索时必须带 tenant 过滤（防越权）
def search(tenant_id: str, user_id: str, query_vec: list, top_k: int = 10):
    return client.search(
        collection_name="user_memory",
        query_vector=query_vec,
        query_filter=Filter(
            must=[
                FieldCondition(key="tenant_id", match=MatchValue(value=tenant_id)),
                FieldCondition(key="user_id", match=MatchValue(value=user_id))
            ]
        ),
        limit=top_k
    )
```

> [!danger] 应用层过滤 ≠ 隔离
> 如果只靠应用代码 `if memory.tenant_id == current_tenant` 过滤，一旦代码 bug 或缓存污染就会跨租户泄露。**必须在存储层用 payload 过滤**，Qdrant/Milvus 都支持，PostgreSQL 用 Row-Level Security。

## 8. 治理层：配额、审计与合规

### 8.1 配额服务（Redis + Lua）

```lua
-- 原子化配额扣减（防超卖）
-- KEYS[1] = quota:{tenant_id}:{user_id}:{day}
-- ARGV[1] = cost (token 数)
-- ARGV[2] = limit

local current = tonumber(redis.call('GET', KEYS[1]) or '0')
local limit = tonumber(ARGV[2])
local cost = tonumber(ARGV[1])

if current + cost > limit then
    return 0  -- 配额不足
end

redis.call('INCRBY', KEYS[1], cost)
redis.call('EXPIRE', KEYS[1], 86400)  -- 24h 重置
return 1
```

### 8.2 三级配额体系

| 级别 | 维度 | 限额示例 | 超限行为 |
|------|------|---------|---------|
| **租户级** | tenant_id + day | 10M tokens/天 | 降级到小模型 + 告警 |
| **用户级** | tenant_id + user_id + day | 100K tokens/天 | 拒绝请求 + 引导升级 |
| **会话级** | session_id | 10K tokens/会话 | 强制收敛（截断上下文） |

### 8.3 审计链路


> [!important] 合规要求

### 13.2 扩容触发条件

| 从 → 到 | 触发指标 | 关键升级 |
|---------|---------|---------|
| 阶段 1 → 2 | DAU > 3K 或 TTFT P95 > 2s | 单点 → 高可用，A100 → H100 |
| 阶段 2 → 3 | DAU > 15K 或 GPU 利用率持续 > 80% | 双 AZ → 三 AZ，引入小模型池分流 |

## 14. 深度分析

### 14.1 为什么不用托管平台（Dify / Coze 企业版）

```
自研 vs 托管的决策分界线：

自研（本方案）适用：
  · 用户 > 5 万，GPU 成本 > $50K/月
  · 需要深度定制（Memory 写回 / Governance 策略）
  · 数据合规要求高（金融 / 政务 / 医疗）
  · 已有 K8s 运维团队

托管适用：
  · 用户 < 1 万，快速验证
  · 标准化场景（客服 / FAQ / 知识库）
  · 无专职 SRE 团队
  · 接受供应商锁定
```

> [!seealso] 托管平台对比
> 详见 [[05-Agent脚手架与快速启动工具生态|../09-Agent框架生态/05-Agent脚手架与快速启动工具生态]] 的低代码平台章节。10 万用户规模下，托管平台的边际成本会超过自研。

### 14.2 10 万用户的真正瓶颈在哪

```
常见误判                    真实瓶颈
─────────────────────       ─────────────────────
"用户数太多"                → 并发会话数（非用户数）
"向量库扛不住"              → 向量库不是瓶颈，GPU 推理才是
"带宽不够"                  → 带宽充裕，GPU 利用率才是关键
"需要更多 Agent"            → Agent 数量不是问题，编排效率才是
```

### 14.3 与四层架构的映射

| 本方案分层 | 四层架构（[[11-生产级Agent四层架构工程落地]]） | 关键扩展 |
|-----------|------------------------------------------|---------|
| 接入层 | —（新增，四层未覆盖） | 多租户网关是规模化刚需 |
| 编排层 | Action 层 | 从单实例 → 集群化 + 状态外置 |
| 推理层 | Brain 层 | 从单模型 → 池化分层 + 路由 |
| 记忆层 | Memory 层 | 从单库 → 四层分层 + 多租户硬隔离 |
| 工具层 | Action 层（工具部分） | 从单沙箱 → 沙箱池 + MCP 网关 |
| 治理层 | Governance 层 | 从策略 → 配额 + 审计 + 成本三维 |
| 观测层 | Governance 层（观测子域） | 从 trace → 三维观测 + 告警 |

### 14.4 关键决策的批判性审视

> [!abstract] 用「The Fool」批判性思维复盘
> 本方案的关键决策值得用 [[06-生产级框架选型批判性决策指南|../09-Agent框架生态/06-生产级框架选型批判性决策指南]] 的五模式再审视一次：
>
> - **Expose My Assumptions**：假设 DAU 30%——企业工具类可能只有 10%（日活骤降，GPU 过度配置）
> - **Argue the Other Side**：为什么不全部用托管？因为 10 万用户的托管费 > 自研 + 运维
> - **Find the Failure Modes**：最可能死在"GPU 扩容冷启动 + 流量突增"——需要预留 30% 冗余
> - **Attack This**：SGLang 真的比 vLLM 好 2-5x？只在 Agent 共享前缀场景，RAG 长文档场景优势消失
> - **Test the Evidence**：成本估算基于 2026 年 8 月 H100 价格，GPU 价格下行可能让方案更激进

## 15. Checklist

### 容量与扩容
- [ ] 是否按 DAU × 会话 × 轮数 × 调用数推导了推理 QPS（而非拍脑袋）？
- [ ] GPU 估算是否区分了主干模型（70B+）和小模型（7B-14B）？
- [ ] HPA 是否用队列深度而非 CPU 作为扩容指标？
- [ ] 是否预留了 5 分钟 GPU 冷启动窗口的缓冲容量？
- [ ] 是否规划了三阶段扩容路径（1 万 → 5 万 → 10 万）？

### 多租户隔离
- [ ] 租户隔离是否在存储层（Qdrant payload / PostgreSQL RLS）而非应用层？
- [ ] 推理集群是否按租户等级分池（企业独占 + 共享）？
- [ ] 配额是否三级（租户 / 用户 / 会话）+ Lua 原子扣减？
- [ ] JWT 中的 tenant_id 是否在 Service Mesh 层二次校验？

### 高可用
- [ ] 是否多 AZ 部署（≥ 2 个 AZ）？
- [ ] Redis 是否 Sentinel / Cluster 模式？
- [ ] 是否定义了降级矩阵（每个组件故障的应对动作）？
- [ ] RTO/RPO 是否满足业务要求？

### 成本治理
- [ ] GPU 成本占比是否控制在 70% 以内（否则优化空间不足）？
- [ ] 是否启用了 SGLang RadixAttention + FP8 量化？
- [ ] 是否按 tenant + user 维度计量 token 成本？
- [ ] 是否规划了 Spot 实例 + 预留实例的混合策略？

### 治理与合规
- [ ] 审计日志是否全量（query + chunks + model_version + tool_calls）？
- [ ] 审计日志是否不可变（Kafka + WORM）+ 可查询（ClickHouse）？
- [ ] 合规遗忘是否 cascade 清理全链路（向量 + KG + trace）？
- [ ] 高敏工具调用是否必须 OpenPolicyAgent 校验 + 人在回路？

### 观测
- [ ] 是否用 OpenTelemetry / OpenInference 埋点（保证后端可换）？
- [ ] 错误请求是否 100% 采样 trace？
- [ ] 关键指标（TTFT / GPU 利用率 / KV cache）是否有告警规则？
- [ ] 成本看板是否按 tenant / agent / tool 维度可下钻？
