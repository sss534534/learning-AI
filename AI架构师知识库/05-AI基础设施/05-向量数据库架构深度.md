## 1. 向量数据库架构全景

### 1.1 为什么不能只用PostgreSQL + pgvector？

| 维度 | pgvector | 专用向量数据库 |
|------|----------|--------------|
| 索引类型 | HNSW, IVFFlat | HNSW + IVF + DiskANN + 量化索引 |
| 数据规模 | < 1000万向量 | 数十亿级 |
| 查询延迟 | 10-100ms | < 10ms (P99) |
| 高可用 | 依赖PG复制 | 原生分布式架构 |
| 过滤能力 | SQL（强大） | 标量+向量混合过滤 |
| 多租户 | 需自行实现 | 原生Partition/Collection级别隔离 |
| 运维复杂度 | PG运维即可 | 专用运维体系 |

**决策规则：**
- 向量 < 100万 + 已有PG → pgvector
- 向量 < 1000万 + 低延迟要求 → Qdrant (单节点)
- 向量 > 1000万 + 高可用 → Milvus (分布式)
- 完全托管 + 免运维 → Pinecone/Zilliz Cloud
- 需要GraphQL原生支持 → Weaviate

### 2.2 数据分片策略

```python
# Milvus 分片配置
collection_config = {
    "collection_name": "semantic_memory",
    "dimension": 1536,                    # OpenAI text-embedding-3-small
    "metric_type": "COSINE",
    "shards_num": 4,                      # 分片数
    "num_partitions": 8,                  # 分区数

    # 分片策略：
    # - shards_num: 数据水平分片，每个分片独立存储+索引
    # - 分片数 = 数据节点数的倍数，建议 2-4倍
    # - 分片过多 → 查询需要合并更多分片
    # - 分片过少 → 写入/索引并行度不够
}

# 基于业务的分区策略
partition_strategies = {
    "time_based": "PARTITION BY RANGE(date_field)",  # 按时间
    "tenant_based": "PARTITION BY LIST(tenant_id)",   # 按租户
    "hot_cold": "热数据(HNSW内存) vs 冷数据(DiskANN)",   # 按热度
}

# 创建分区的代码示例
from pymilvus import Collection, Partition

collection = Collection("semantic_memory")
collection.create_partition("tenant_a")
collection.create_partition("tenant_b")

# 写入时指定分区
collection.insert(data, partition_name="tenant_a")
# 查询时可以限定分区，大幅减少扫描范围
collection.search(
    vectors,
    anns_field="embedding",
    param={"nprobe": 16},
    limit=10,
    partition_names=["tenant_a"],  # 仅扫描租户A的数据
)
```

### 2.3 索引策略矩阵

| 索引类型 | 适用场景 | 内存占用 | 构建速度 | 查询速度 | 精度 |
|---------|---------|---------|---------|---------|------|
| **FLAT** | < 10万，追求100%精度 | 高 | 即时 | O(n) 慢 | 100% |
| **IVF_FLAT** | 百万级，平衡精度/速度 | 中 | 快 | O(log n) | 95-99% |
| **IVF_SQ8** | 内存受限，百万级 | 低(压缩8x) | 中 | O(log n) | 90-95% |
| **IVF_PQ** | 内存严重受限，千万级 | 极低(压缩16x+) | 慢 | O(log n) | 85-92% |
| **HNSW** | 千万级，追求低延迟 | 高 | 慢 | O(log n) 极速 | 98-99% |
| **DiskANN** | 十亿级，大容量 | 极低(磁盘) | 慢 | 中 | 95-98% |

```python
# 索引创建实战
index_params = {

        "params": {

    },

        "params": {
            "nlist": 2048,    # 聚类数量 (√n 起步)
            "nprobe": 32,     # 查询时探测聚类数
        }
    },

    # 场景3: 十亿级 (磁盘索引)
    "billion_scale": {
        "index_type": "DISKANN",
        "metric_type": "COSINE",
        "params": {
            # DiskANN 自动管理
        }
    },
}

# 查询参数调优
search_params = {
    "HNSW": {"ef": 128},              # > k 且越大越精确越慢

}
results = collection.search(
    query_vectors,
```

## 3. Qdrant：高性能Rust向量数据库

### 3.1 架构亮点

```rust
// Qdrant 的核心数据结构
struct Segment {
    id: SegmentId,
    vector_storage: VectorStorage,  // 向量数据
    payload_index: PayloadIndex,    // 标量过滤索引
    hnsw_index: HnswIndex,         // HNSW图索引
    version: u64,                   // 乐观锁版本号
}

// 分段策略
enum SegmentType {
    Plain,       // 可写段：新数据写入
    Indexed,     // 已索引段：HNSW构建完成
    Compacted,   // 合并后的段
}
```

**Qdrant 设计哲学：**
- **Rust实现**：零成本抽象 + 无GC = 低延迟可预测
- **WAL先行写入**：写入先到WAL（Write-Ahead Log），异步构建索引
- **段不可变**：写入后段只读，通过新建段实现更新
- **量化压缩**：Scalar Quantization / Product Quantization / Binary Quantization

### 3.2 集合配置

```python
from qdrant_client import QdrantClient
from qdrant_client.models import (
    Distance, VectorParams, OptimizersConfigDiff,
    HnswConfigDiff, QuantizationConfig, ScalarQuantization,
)

client = QdrantClient(host="localhost", port=6333)

# 生产级集合配置
client.create_collection(
    collection_name="production_knowledge",
    vectors_config=VectorParams(
        size=1536,
        distance=Distance.COSINE,
        on_disk=True,  # 向量存储在磁盘（节省内存）
    ),

    # HNSW 索引配置
    hnsw_config=HnswConfigDiff(
        m=16,                    # 每节点连接数
        ef_construct=100,        # 构建时搜索宽度
        full_scan_threshold=10000,  # < 此数量直接用暴力搜索
        max_indexing_threads=4,
        on_disk=True,            # HNSW图存储在磁盘
    ),

    # 量化配置（可选，大幅减少内存）
    quantization_config=ScalarQuantization(
        scalar=ScalarQuantizationConfig(
            type=ScalarType.INT8,
            quantile=0.99,        # 忽略1%的异常值
            always_ram=True,      # 量化后的向量在内存中
        ),
    ),

    # 优化器配置
    optimizers_config=OptimizersConfigDiff(
        default_segment_number=2,
        max_segment_size=200000,   # 每段最多20万向量
        memmap_threshold=50000,    # 超过5万使用mmap
        indexing_threshold=20000,  # 超过2万开始构建HNSW
        flush_interval_sec=5,      # 每5秒刷盘
    ),

    # 写入一致性
    shard_number=3,                # 分片数
    replication_factor=2,          # 副本数 (新版本)
    write_consistency_factor=2,    # 至少2个副本确认写入
)
```

## 5. Weaviate：GraphQL原生的向量数据库

### 5.1 特色架构

Weaviate的核心差异化在于它的 **Class-Property** 数据模型和原生 **GraphQL** 接口：

```graphql
# Weaviate GraphQL 查询示例：向量搜索 + 条件过滤 + 关系图遍历
{
  Get {
    Article(
      nearText: {
        concepts: ["machine learning infrastructure"]
      }
      where: {
        operator: And
        operands: [
          { path: ["status"], operator: Equal, valueString: "published" }
          { path: ["wordCount"], operator: GreaterThan, valueInt: 500 }
        ]
      }
      limit: 10
    ) {
      title
      content
      author {
        ... on Author {     # 跨Class关系遍历
          name
          institution
        }
      }
      _additional {
        distance
        certainty          # Weaviate特有的确定性分数
      }
    }
  }
}
```

## 6. 性能调优实战

### 6.1 索引参数调优公式

```
HNSW 参数调优：
- M (每节点连接数): 12-64
  内存 ≈ M × 2 × dim × 4 bytes × n_vectors
  精度: M↑ → 精度↑, 内存↑
  建议: dim < 512 → M=32; dim > 1024 → M=16

- efConstruction (构建搜索宽度): 100-500
  构建时间 ∝ efConstruction × M
  建议: 生产环境 200-300, 开发环境 100

- ef (查询搜索宽度): k ~ 1024
  查询延迟 ∝ ef
  精度: ef↑ → 精度↑
  建议: ef = max(k, 64), 通常 128-256

IVF 参数调优：
- nlist (聚类数):
  建议: nlist = 4 × √n_vectors
  示例: 100万向量 → nlist ≈ 4096

- nprobe (查询探测数):
  查询延迟 ∝ nprobe
  精度: nprobe↑ → 精度↑
  建议: 0.5% ~ 2% of nlist
```

### 6.2 量化压缩对比

| 量化类型 | 压缩比 | 精度损失 | 内存节省 | 最佳场景 |
|---------|--------|---------|---------|---------|
| 无量化 (FLOAT32) | 1x | 0% | 0% | 精度优先 |
| INT8 Scalar Quantization | 4x | < 1% | 75% | 通用推荐 |
| Product Quantization (PQ) | 8-32x | 2-10% | 87-97% | 大规模(亿级) |
| Binary Quantization | 32x | 5-15% | 97% | 超大规模，精度可接受 |

```python
# 量化配置决策
def choose_quantization(total_vectors, dim, memory_budget_gb):
    """根据规模自动选择量化策略"""
    raw_memory = total_vectors * dim * 4 / (1024**3)  # GB

    if raw_memory <= memory_budget_gb:
        return {"type": "none", "memory_gb": raw_memory}

    sq_memory = total_vectors * dim * 1 / (1024**3)
    if sq_memory <= memory_budget_gb:
        return {"type": "SQ8", "memory_gb": sq_memory, "accuracy": ">99%"}

    pq_memory = total_vectors * dim * 0.25 / (1024**3)
    if pq_memory <= memory_budget_gb:
        return {"type": "PQ", "memory_gb": pq_memory, "accuracy": "90-98%"}

    return {"type": "Binary", "memory_gb": total_vectors * dim / 8 / (1024**3),
            "accuracy": "85-95%"}
```

### 6.3 混合搜索（向量 + 关键词）

```python
class HybridSearchEngine:
    """向量搜索 + BM25关键词搜索 + 融合排序"""

    def __init__(self, vector_db, text_index):
        self.vector_db = vector_db  # Milvus/Qdrant等
        self.text_index = text_index  # Elasticsearch/BM25

    def search(self, query: str, top_k: int = 10,
               alpha: float = 0.7) -> List[dict]:
        """
        alpha: 向量搜索权重 (0-1)
        1-alpha: 关键词搜索权重
        """
        # 1. 向量搜索
        query_emb = self.embed(query)
        vector_results = self.vector_db.search(
            query_emb, limit=top_k * 2
        )

        # 2. BM25关键词搜索
        text_results = self.text_index.search(
            query, size=top_k * 2
        )

        # 3. 分数归一化
        vector_scores = self._normalize(vector_results)
        text_scores = self._normalize(text_results)

        # 4. 融合排序 (加权求和)
        fused = {}
        for doc_id, v_score in vector_scores.items():
            t_score = text_scores.get(doc_id, 0)
            fused[doc_id] = alpha * v_score + (1 - alpha) * t_score

        for doc_id, t_score in text_scores.items():
            if doc_id not in fused:
                fused[doc_id] = (1 - alpha) * t_score

        # 5. 排序返回
        sorted_results = sorted(fused.items(),
                               key=lambda x: x[1], reverse=True)
        return [{"id": doc_id, "score": score}
                for doc_id, score in sorted_results[:top_k]]

    def _normalize(self, results, method="min_max"):
        """分数归一化到[0,1]"""
        scores = [r["score"] for r in results]
        if method == "min_max":
            min_s, max_s = min(scores), max(scores)
            return {r["id"]: (r["score"] - min_s) / (max_s - min_s + 1e-8)
                    for r in results}
        elif method == "rff":
            # Reciprocal Rank Fusion
            return {r["id"]: 1.0 / (rank + 60)
                    for rank, r in enumerate(results)}
```

## 7. 选型决策矩阵

### 7.1 场景-数据库速配

| 场景 | 推荐 | 核心理由 |
|------|------|---------|
| 个人项目 / PoC | Qdrant | 单二进制部署，零依赖，Rust高性能 |
| 中小团队 RAG | Qdrant / Weaviate | 运维简单，功能丰富 |
| 企业级 RAG 平台 | Milvus | 分布式架构，水平扩展，云原生 |
| 完全免运维 | Pinecone / Zilliz Cloud | Serverless，按量付费 |
| GraphQL 技术栈 | Weaviate | 原生GraphQL，RESTful + GraphQL双接口 |
| 中文场景 | Milvus（国产） | 中文社区活跃，Zilliz支持 |
| 多模态检索 | Weaviate | 多向量原生支持 |
| 超过10亿向量 | Milvus + DiskANN | 磁盘索引，成本可控 |
| 边缘部署 | Qdrant (单节点) | 资源占用低，可运行在树莓派 |

### 7.2 成本模型

```
TCO = 计算成本 + 存储成本 + 运维成本 + 网络成本

自托管 Milvus (1000万向量, 1536维):
├── 计算: 3 × Query Node (8C16G) = ¥2,500/月
├── 计算: 3 × Data Node (16C32G)  = ¥4,800/月
├── 存储: 1TB S3                    = ¥200/月
├── 消息队列: Pulsar 3节点          = ¥1,500/月
├── 元数据: etcd 3节点              = ¥1,000/月
├── 运维人力: 0.3 FTE               = ¥4,500/月
└── 总计: ≈ ¥14,500/月

Pinecone Serverless (1000万向量, 1536维):
├── 存储: 1000万 × 1536 × 4B = ~61GB → $0.33/GB = $20/月
├── 写入: 按次 → 视更新频率
├── 读取: 按次 → 视查询量
└── 总计: $30-300/月 (视用量)

决策规则：
- 查询量确定: 自托管便宜
- 查询量波动大: Serverless更经济
- 数据量大查询少: Serverless
- 数据量小查询大: 自托管
```

## 总结

向量数据库选型不是"哪个最好"的问题，而是**"哪个最匹配你的场景"**：

- **小团队 → Qdrant**：运维成本最低，性能极佳
- **企业平台 → Milvus**：分布式架构，生态完善
- **免运维 → Pinecone/Zilliz Cloud**：专注业务
- **GraphQL → Weaviate**：数据模型最丰富

核心运维要点：**索引选型决定性能上限，分片策略决定扩展能力，一致性配置决定可用性**。
