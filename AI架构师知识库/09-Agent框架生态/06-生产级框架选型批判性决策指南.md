## 1. 模式一：暴露我的假设（苏格拉底式提问）

### 1.1 "生产级"这四个字到底是什么意思？

任何不先定义"生产级"的选型结论都是耍流氓。对生产级的不同定义，直接指向完全不同的最优解：

| 你口中的"生产级"是 | 正确答案 |
|------------------|---------|
| **跑起来不崩、能断点恢复、能回溯调试** | → **LangGraph**（Checkpoint + 时间回溯是硬证据，其他框架要么没有要么只补了壳） |
| **两周内给业务部门上线、不需要严格工程化** | → **CrewAI + Dify**（开发速度压倒一切，出问题人工兜底） |
| **符合金融/政企合规、有审计日志、RBAC、Entra ID** | → **Microsoft Agent Framework** 或 **Google ADK** |
| **全栈 TS、和 Next.js 前端无缝部署** | → **Mastra**（TS 原生，SSR 友好） |
| **1000+ 并发 QPS、SRE 能接手、运维文档齐全** | → LangGraph 或**裸写 Function Calling + 自研**，所有脚手架 CLI 都不合格 |
| **成本可控、Token 可审计、不会一个请求花 \$50** | → LangGraph + 成本治理层，或带预算控制的托管服务 |

> [!tip] 行动建议
> 选型会前，团队先花 30 分钟，给"生产级"的 6 个维度打分（1-5 分），**按总分排序再选型**。不要先挑框架再回头找理由。

### 1.2 脚手架 vs 框架的产出幻觉

| 假设（幻觉） | 事实 |
|-------------|------|
| "AgentStack 生成的项目就是生产就绪" | 错。只完成了项目结构和依赖配置，约等于生产就绪的 **15%** |
| "GitHub Stars 多 = 生产可用" | 错。Stars 是虚荣指标，代表"有人看过/标过"，不代表"有人跑在生产" |
| "先 CrewAI MVP，生产时再迁 LangGraph 很简单" | 错。迁移成本约是原项目的 60-90%（执行模型完全不同：角色 → 图） |
| "低代码平台搭的东西不行，还是得写代码" | 不一定。Dify/FlowHunt 的企业用户案例中，约 30-40% 的内部 Agent 需求**不需要写代码也能稳定跑** |

## 2. 模式二：钢人论证（Argue the Other Side）

> 钢人规则：给每个"推荐选项"的反对者最强的论据。只有推翻了最强的反面论证，推荐才站得住。

### 2.1 为什么 LangGraph（通用生产推荐）可能是错误选择

**钢人论据（反对 LangGraph 的最强版本）：**

1. **过度设计杀手**：你一个三步骤的客服工单 Agent，引入 StateGraph + Checkpoint + LangSmith 整套 = 3 个人能干完的活变成 10 个人。学习曲线陡峭到团队**三个月还没产出首版**，期间业务方用 CrewAI 原型已经跑通了两个季度的营收。
2. **API 迭代债**：LangChain 家族历史上 API 频繁变动，0.1 → 0.2 升级时大面积 breaking change。你今天写的图定义，6 个月后框架新版可能要求迁移到 StateReducer 模式。
3. **半锁定**：要拿全生产能力，就得用 LangSmith + LangGraph Platform 付费托管层。框架可替换性在理论上，不在实际上。
4. **反例事实**：很多稳定的生产 Agent 系统（早期 Stripe 客服、部分金融自动化）是**裸写 Function Calling + Redis 队列**，稳定性反而比用 LangGraph 的高 2 倍——因为少了一层抽象和潜在的框架 bug。

### 2.2 为什么 CrewAI（快速上手）可能是错误选择

**钢人论据：**

1. **第 8 周悬崖**：1-7 周爽飞，5 行代码跑 demo。第 8 周遇到复杂分支/循环/人工介入审批，框架抽象卡住你，**重写成本是直接写 LangGraph 的 2.5x**。
2. **长任务杀手**：一个 2 小时的长研究任务跑到第 1 小时 50 分钟崩了——**没有 checkpoint，从头再跑**，一次 \$50，重复三次直接被财务拉黑。
3. **可观测性黑洞**：CrewAI 的可视化面板是"开发级"的，不是"生产级"的。出了问题要定位，你还是得自己接 OTel + LangSmith，等于白嫖了框架的一半优势。
4. **角色幻觉陷阱**：`backstory="资深研究专家"` 不等于真的资深。角色定义是 Prompt 糖衣，不是模型能力倍增器。很多团队把时间花在"调 backstory"而非真正的评估和工具设计上。

### 2.3 为什么 Microsoft Agent Framework（企业合规）可能是错误选择

**钢人论据：**

1. **Azure 绑定 = 多云战略死刑**：MAF 的合规能力是建立在 Entra ID + Purview + Azure Monitor 之上的。如果公司未来要迁移到阿里云或 AWS，迁移成本是原项目的 **4 倍以上**。
2. **GA 才 4 个月（2026-04），真实验收案例极少**：微软背书不等于生产验证。早期 AutoGen 用户在迁移到 MAF 过程中踩过的坑（对话状态格式不兼容、Tool 签名变更），目前还没有完整的公开沉淀。
3. **跨语言通信 = 复杂度倍增**：MAF 支持 .NET/Python 跨语言 Agent 通信，听起来很美。实际生产中，跨语言 RPC 的调试难度、性能开销、错误定位成本，**远超只用单一语言的系统**。

## 3. 模式三：前期死后分析（Find the Failure Modes）

> 规则：假设一年后项目已经死了，写尸检报告。倒推出每个选型的最可能死法。

### 3.1 每个选型的"死因"

| 选型 | 最可能死因（尸检结论） | 出现概率 | 提前预防 |
|------|---------------------|---------|---------|
| **LangGraph** | 团队工程能力跟不上，调试和状态推理成本超过 Agent 业务价值，项目延期 6 个月被砍 | 25% | 做 2 周 PoC，用实际任务复杂度验证团队能否 handle |
| **CrewAI** | 长任务崩了无 checkpoint，API 费用浪费超过 30%；复杂分支无法表达 → 重写 LangGraph → 错过上线窗口 | 35%（最高） | 关键任务必须加 checkpoint；5 步以上直接上 LangGraph |
| **Microsoft Agent Framework** | 深度绑定 Azure，和公司多云战略冲突；或迁移 bug 太多，用户流失 | 20% | 隔离 Microsoft Graph 调用层；至少 3 个核心场景在 GA 后验证过 |
| **Mastra (TS)** | TS 生态 model provider 工具调用能力弱于 Python，复杂工具场景写桥接层，技术债膨胀 | 25% | 先跑 100 条实际工具调用基准测试 |
| **AgentStack 脚手架** | 生成的骨架 + 底层框架升级冲突，两套标准互不兼容，维护成本 > 手搭项目 | 15% | 生成后立即脱离 CLI，别用 generate/upgrade 命令 |
| **Dify 低代码** | 业务需求变更快，低代码平台表达力到达天花板，迁移到框架项目 | 20% | 选型前预估未来 6 个月变更需求，边界场景做可行性验证 |
| **裸写 Function Calling + 自研** | 团队无经验，轮子一个一个重造，造的还不如框架成熟，时间窗口关闭 | 40%（最高） | 除非 QPS 极高 + SRE 团队强，否则别走这条路 |

## 4. 模式四：红队对抗分析（Attack This）

> 规则：我是你的对手，要让你的选型决策失败。我最可能在以下 3 个点上动手脚（也是选型者最常掉的坑）。

### 4.1 选型时最容易犯的 3 个致命错误

| 错误 | 为什么致命 | 反制措施 |
|------|-----------|---------|
| **① 把 GitHub Stars 当生产证据** | Hermes 172K、OpenClaw 375K 颗星，但它们是"个人助理"类 agent，**做客服工单生产部署两个都不合格**。Stars 是全球社区标星总数，不代表你的场景被验证过。 | 看「谁在用」而非「多少人标星」。Uber/Klarna/LinkedIn 用 LangGraph 是硬证据。找和你行业/场景一致的 2-3 个公开案例。 |
| **② 把"学习曲线低"排进前三个决策因素** | CrewAI 一周出 demo，第 8 周开始框架能力顶不住，重写成本是直接选 LangGraph 的 2.5 倍。"前期速度快"是选型陷阱——**慢启动快扩展的框架，长期总时间比快启动慢扩展的更短**。 | 如果你的任务超过 5 个步骤，或需要人工介入审批，直接选 LangGraph。复杂度低于 3 步才选 CrewAI。 |
| **③ 忽略 p99 延迟和 API 成本** | 所有框架 demo 只测 happy path。真实生产中 5% 的请求会触发 10+ 轮工具调用，费用是平均的 15 倍。上线一周后财务找你谈话。 | 选前必须做 100 条真实数据的 cost/latency 基准测试，测 p95/p99 而非平均。引入 Token 预算控制层。 |

> [!danger] 红队攻击剧本
> 我（对手）会在选型评审会上只展示 CrewAI demo 的 5 行代码、LangGraph 的 Uber 案例、MAF 的合规文档——**单独看都是对的，合在一起让你忽略场景错配**。你如果不逐条对照自己的真实任务复杂度、未来 6 个月需求曲线、p99 成本预算，就会上钩。

## 5. 模式五：证据评估（Test the Evidence）

### 5.1 "生产使用/生产就绪"说法可信度评级

| 说法 | 可信度 | 评级理由 |
|------|-------|---------|
| "LangGraph 在 Uber、Klarna、LinkedIn 生产使用" | **A（高）** | 有公开演讲、LangGraph Platform 客户案例、月下载量千万级（非 GitHub 虚荣指标） |
| "CrewAI 50K+ stars 生产就绪" | **B（中）** | Stars 多但复杂耐久场景公开案例少；大部分是原型/内容生成；持久化最近才补完 |
| "Microsoft Agent Framework 1.0 GA 企业就绪" | **B+（中高）** | 微软背书 + AutoGen 存量迁移，但 GA 才 4 个月，金融/政企真实验收案例还少 |
| "AgentStack 生成的项目生产就绪" | **D（低）** | 这是营销语言。生成的是骨架，不是经过压力测试的系统 |
| "Mastra TS-first 生产可用" | **B-（中）** | TS 场景确实方便，但模型工具生态成熟度落后 Python 约 1-2 个季度 |
| "Dify/Coze 企业级生产可用" | **A-（高）** | 有国内大量企业客户案例（Dify > 1000 家付费用户），但 SLA 取决于部署方式 |

### 5.2 量化生产能力四维度评分

> 评分说明：1-5 分。分数越高越"生产级"。四个维度：**生产成熟度、耐久性（断点恢复）、可观测性、企业治理（合规/RBAC/审计）**。

| 框架/平台 | 生产成熟度 | 耐久性 | 可观测性 | 企业治理 | 加权总分（权重 3/3/2/2） |
|----------|:---------:|:------:|:--------:|:--------:|:---------------------:|
| LangGraph | 5 | 5 | 4.5 | 3 | **4.55** |
| Microsoft Agent Framework | 4 | 4 | 4.5 | 5 | **4.40** |
| Google ADK + agents-cli | 4 | 4 | 4 | 4.5 | **4.10** |
| CrewAI | 4 | 3 | 3.5 | 2.5 | **3.40** |
| Mastra | 3 | 3.5 | 3.5 | 2.5 | **3.15** |
| Hermes Agent（开源） | 4 | 3.5 | 3 | 2 | **3.25** |
| Dify（自托管企业版） | 4 | 3.5 | 4 | 4.5 | **3.95** |

> [!note] 评分解读
> 单项第一不代表总分第一。LangGraph 在"耐久性"上无敌（Checkpoint 是真生产能力），但在"企业治理"上不如微软/Google/Dify——这些是真金白银的合规差异，不是噱头。

## 6. 最终决策：按实际场景对号入座

经过五模式批判后，不是"谁最好"，而是**"在你的约束下，谁的致命缺点你最能接受"**。

### 6.1 选型决策矩阵（最终版）

| 你的实际情况（逐条对） | 最佳方案 | 配套脚手架/部署 | 最要小心的坑 |
|---------------------|---------|----------------|------------|
| **复杂长任务（>5步）、状态不能丢、需人工介入审批、合规审计** | **LangGraph** | 直接 `pip install langgraph`，不要用 AgentStack 包一层 | 团队工程能力跟不上 → 先 PoC 两周 |
| **明确多角色工作流（调研→撰写→审核）、任务线性分解、<5步** | **CrewAI** | `agentstack init` 选 CrewAI 快速起，但**自己补 checkpoint 层** | 第 8 周复杂度悬崖 → 提前设计迁移预案 |
| **.NET 技术栈 / Azure / Entra ID / 金融政企合规** | **Microsoft Agent Framework** | 官方模板 + Azure SDK | 多云锁定 → 隔离 Microsoft Graph 调用层 |
| **TS 全栈 / 需嵌入 Web / Next.js SSR 友好** | **Mastra** | `npm create mastra@latest` | 复杂工具场景桥接 → 先跑 100 条基准 |
| **GCP / Gemini / Java 支持 / 多语言 A2A** | **Google ADK + agents-cli** | `agents-cli scaffold` | 第三方模型弱 → 确认模型锁定可接受 |
| **不想写代码 / 业务部门自搭 / 知识库问答内部工具** | **Dify** | 直接部署低代码平台，别碰框架 | 表达力天花板 → 预估 6 个月变更需求 |
| **金融政企合规 + 已私有化部署 Kubernetes** | **Dify 企业版 或 StackAI** | Helm/K8s 部署 + SSO/RBAC | 供应商锁定 → 对比 2-3 家 |
| **QPS 极高（1000+）、极致性能、SRE 团队强** | **原生 Function Calling + 自研** | 无框架，用 FastAPI/gRPC + Redis | 造轮子陷阱 → 团队需有至少 1 个 agent 老兵 |
| **不确定 / 团队全是新手 / 先搞清楚需求再说** | **先 CrewAI 跑 MVP，2 个月后定框架** | `agentx new --enterprise` 起模板 | 2 个月到期必须做框架决策，不要无限期 CrewAI 下去 |

### 6.2 迁移策略：CrewAI → LangGraph 的两阶段路线

约 60% 的团队最终路径是「先 CrewAI MVP → 后 LangGraph 生产」。迁移不是重写，按以下步骤可以节省 40% 工作量：

```
阶段一：边界分离（MVP 阶段就要做）
  └── 工具调用逻辑 → 独立 tools/ 模块，不嵌在 Agent 里
  └── Prompt 模板 → 独立 prompts/*.yaml，不写在 backstory 字符串里
  └── 业务决策（什么时候走下一步）→ 独立 decision_service.py，不放在 CrewAI 的 Process 里

阶段二：图映射（生产迁移）
  └── 每个 Agent → 映射到 LangGraph 一个 Node
  └── Task 的顺序/依赖 → 映射到 Edge / ConditionalEdge
  └── Crew 共享上下文 → 映射到 State（TypedDict）
  └── Phase 一独立出来的 tools/prompts/decision → 原样复用

时间预估：中等复杂度（5 Agent + 8 Task）≈ 1.5-2 周
不做 Phase 一分离直接迁移：≈ 4 周，且 bug 率翻倍
```

## 7. Checklist

### 选型前（必须全部 Yes 才能进入评估）
- [ ] 已给"生产级"六维度（稳定/速度/合规/并发/成本/治理）打过分并排了序
- [ ] 已区分「我要的是脚手架」还是「我要的是框架」
- [ ] 已用钢人论证（模式二）推翻过至少 1 个自己最初的偏好
- [ ] 已用前期死后分析（模式三）识别出 2-3 个最可能死因
- [ ] 已准备 100 条真实数据做 cost/latency 基准测试

### 评估中
- [ ] 对每个候选框架，已找到 2 个和你行业/场景一致的公开生产案例
- [ ] 已对比 p95/p99 成本，而不只是平均成本
- [ ] 已验证框架的 checkpoint/耐久能力（故意杀掉运行中的长任务，看能否恢复）
- [ ] 已计算 1 年 TCO：框架许可费 + 基础设施 + 运维人力 + API 费用
- [ ] 已做 2 周 PoC，不只是看 demo 视频

### 决策后
