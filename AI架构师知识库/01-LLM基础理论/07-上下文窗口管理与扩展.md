## 1. 为什么上下文窗口是AI架构师的必答题

上下文窗口（Context Window）是LLM的"工作记忆"上限。过去两年，窗口长度从4K→128K→1M→无限，经历了堪比摩尔定律的增长速度。但窗口越大，计算和存储成本呈 **O(n²)** 上升——架构师必须理解窗口管理的全链路技术栈。

| 阶段 | 代表模型 | 窗口长度 | 关键技术创新 |
|------|----------|----------|-------------|
| 2022 | GPT-3.5 | 4K | 绝对位置编码 |
| 2023 | GPT-4-32K, Claude 100K | 32K–100K | RoPE + 插值 |
| 2024 | GPT-4o 128K, Gemini 1.5 Pro | 128K–1M | RingAttention, 混合架构 |
| 2025 | Gemini 2.0, Claude 4 | 200K–2M | Infini-attention, 动态稀疏 |
| 2026 | GPT-5 (预期) | 1M+ | 层次化记忆 + 自适应压缩 |

## 2. 位置编码 — 让模型"知道顺序"

### 2.1 演化路线图

```
绝对位置编码 (Sinusoidal/Learned)
    ↓ 长度不灵活，泛化差
相对位置编码 (T5 Bias, Shaw et al.)
    ↓ 计算开销大
RoPE (Rotary Position Embedding)
    ↓ 成为主流，天然支持相对位置
ALiBi (Attention with Linear Biases)
    ↓ 零成本外推，但精度略低
YaRN / NTK-aware / LongRoPE
    ↓ RoPE的扩展补丁
NoPE (No Positional Encoding)
    ↓ 最新趋势：足够数据训练即可隐式学习
```

### 2.2 RoPE 深度解析

RoPE（Su et al., 2021）通过旋转变换将位置信息融入Q/K向量：

```
核心公式:
  q_m = R(θ, m) · W_q · x_m
  k_n = R(θ, n) · W_k · x_n
  a_{m,n} = q_m^T · k_n = x_m^T W_q^T R(θ, m-n) W_k x_n

旋转矩阵R(θ, m)在二维子空间上分别旋转m·θ_i角度
频率 θ_i = base^{-2i/d}, 典型 base=10000
```

**RoPE的优势**:
- 位置信息衰减与相对距离相关（远距离token交互自然减弱）
- 可扩展到训练时未见过的长度（通过各种插值方法）
- 计算高效（可与Attention合并为矩阵乘法）

### 2.3 扩展方法对比

| 方法 | 原理 | 适用场景 | 精度损失 | 复杂度 |
|------|------|----------|----------|--------|
| **线性插值 (PI)** | 将位置索引线性缩小: m→m/k | 4K→32K | 中等 | 低 |
| **NTK-aware** | 调整RoPE base: 10000→500000 | 4K→16K | 低 | 极低 |
| **YaRN** | NTK-aware + 温度缩放 | 4K→128K | 极低 | 低 |
| **LongRoPE** | 进化搜索最优base+scale | 256K→2M | 极低 | 高 |
| **Self-Extend** | 分组注意力：近距全注意+远距分组 | 通用 | 低 | 中 |
| **ReRoPE** | 矩形窗口+指数衰减 | >训练长度 | 低 | 中 |
| **DCA (Dual Chunk)** | 块内全注意+块间位置调整 | 超长文档 | 低 | 低 |

### 2.4 YaRN 实现要点

```python
# YaRN 核心：NTK-aware缩放 + 温度因子
def yarn_rope_freqs(dim, max_len, original_max_len, scale_factor):
    # 1. NTK-aware: 调整base
    alpha = scale_factor ** (dim / (dim - 2))
    base = 10000 * alpha
    
    # 2. 计算频率
    theta = 1.0 / (base ** (torch.arange(0, dim, 2) / dim))
    
    # 3. YaRN温度校正
    # 对高频维度（低theta）维持原样，对低频维度（高theta）插值
    beta_fast = 32
    beta_slow = 1
    gamma = (theta - min_theta) / (max_theta - min_theta)
    smooth = (1 + torch.tanh(beta_fast * (gamma - 0.5))) / 2
    temperature = 1 + smooth * (scale_factor - 1)
    
    return theta / temperature
```

## 3. KV Cache — 推理加速的核心

### 3.1 为什么需要KV Cache

自回归生成中，每个新token需要attend之前的所有token。如果没有缓存，每个生成步骤都需要重新计算所有历史token的K/V——O(n²)的计算量。

**KV Cache原理**:
```
Step 1: 输入 "The cat" → 计算 K₁, V₁ → 缓存 [K₁], [V₁]
Step 2: 输入 "sat"   → 只计算K₂, V₂ → 用 [K₁,K₂], [V₁,V₂] 计算attention
Step 3: 输入 "on"    → 只计算K₃, V₃ → 用 [K₁,K₂,K₃], [V₁,V₂,V₃]
...
```

### 3.2 内存模型

单层KV Cache内存量：

```
Memory_per_layer = 2 × batch_size × seq_len × num_heads × head_dim × dtype_bytes

示例 (Llama-2-7B, bfloat16, batch=1):
  层数: 32
  num_kv_heads (GQA): 8
  head_dim: 128
  dtype: 2 bytes
  
  8K context: 2 × 1 × 8192 × 8 × 128 × 2 = 33.5 MB × 32层 ≈ 1.07 GB
  128K context: 2 × 1 × 131072 × 8 × 128 × 2 ≈ 17.2 GB (单batch!)
  
  批量推理 (batch=32 @ 128K): 需要 550 GB — 完全不可行
```

### 3.3 KV Cache 压缩技术全景

#### 3.3.1 量化压缩

| 方法 | 精度 | 压缩比 | 实现复杂度 | 代表工作 |
|------|------|--------|-----------|----------|
| **KIVI** | INT2/INT4 per-channel | 4-8x | 中 | KIVI (2024) |
| **KVQuant** | INT3/INT4 + 敏感度感知 | 4-6x | 中 | KVQuant (2024) |
| **Atom** | INT2 + 动态per-token量化 | 6-8x | 较高 | Atom (2024) |
| **FlexGen** | INT4 + CPU offload | 4x | 低 | FlexGen (2023) |
| **FP8 KV** | FP8 (H100原生支持) | 2x | 极低 | NVIDIA TransformerEngine |

#### 3.3.2 结构性压缩

```
方法分类:
┌─ 令牌丢弃 (Token Dropping)
│  ├─ StreamingLLM: 保留前N个+后N个token
```

### 3.4 PagedAttention — vLLM的革命性贡献

PagedAttention将KV Cache管理类比为操作系统的虚拟内存分页：

```python
# PagedAttention 核心思想
"""
传统: 为每个请求预分配连续的max_len大小KV Cache
  → 浪费: 实际生成长度 < max_len
  → 碎片: 多请求导致内存碎片
  → 限制: 无法高效共享prefix

PagedAttention: 将KV Cache分成固定大小的"页面" (block)
  → 按需分配: 只分配实际使用的页面
  → 零碎片: 所有页面大小相同
  → 共享: 多请求共享同一prefix的KV页面
  → 内存效率: 提升 2-4x
"""

# 页面结构示例
class KVCacheBlock:
    def __init__(self, block_size=16):
        self.block_size = block_size
        self.k_cache: Dict[int, Tensor] = {}  # layer_id -> K tensor
        self.v_cache: Dict[int, Tensor] = {}  # layer_id -> V tensor
        self.ref_count: int = 0  # 引用计数，支持共享

class PagedKVCache:
    def __init__(self, num_blocks, block_size, num_layers, num_heads, head_dim):
        self.block_size = block_size
        self.free_blocks = [KVCacheBlock(block_size) for _ in range(num_blocks)]
        self.used_blocks: Dict[int, List[KVCacheBlock]] = {}
    
    def allocate(self, seq_id: int, num_tokens: int) -> List[KVCacheBlock]:
        """按需分配页面"""
        blocks_needed = ceil(num_tokens / self.block_size)
        allocated = []
        for _ in range(blocks_needed):
            block = self.free_blocks.pop()
            allocated.append(block)
        self.used_blocks[seq_id] = allocated
        return allocated
    
    def share_prefix(self, src_seq_id: int, dst_seq_id: int):
        """共享前缀KV Cache页面"""
        self.used_blocks[dst_seq_id] = self.used_blocks[src_seq_id].copy()
        for block in self.used_blocks[dst_seq_id]:
            block.ref_count += 1
```

## 4. 长上下文扩展技术

### 4.1 序列并行 — 突破单卡显存

当序列极长时（100K+），即使KV Cache压缩也不够——需要在多卡间切分计算。

#### RingAttention（环形注意力）

```
工作原理:
将Q/K/V沿序列维度切分到N个设备上

Step 1: 每个设备持有 Q_local, K_local, V_local
Step 2: 计算 local attention: softmax(Q_local × K_local^T) × V_local
Step 3: 环形传递K/V块到下一设备
Step 4: 继续计算 cross attention
Step 5: 重复N次直到K/V环回

通信量: O(N) 次 P2P 传输
显存: 每个设备只需 1/N 的KV Cache
```

#### StripedAttention（条纹注意力）

```
改进RingAttention的负载均衡:

将序列交错分配（条纹状），而非连续分配
→ 每块内部token分布均匀
→ 避免边界效应
→ 减少通信次数
```

#### DeepSpeed Ulysses

```
在注意力头维度切分（而非序列维度）:
  - 计算attention时 All-to-All 通信转为序列切分
  - 计算完再转回头维度
  - 适合大head数场景
```

### 4.2 稀疏注意力架构

| 架构 | 模式 | 复杂度 | 代表 |
|------|------|--------|------|
| **Sliding Window** | 固定窗口w，窗口外不看 | O(n·w) | Mistral, Gemma |
| **Dilated Sliding Window** | 间隔d的滑动窗口 | O(n·w) | Longformer |
| **Global + Local** | 少数global token + 局部窗口 | O(n·w + n·g) | BigBird, ETC |
| **Sparse Sinkhorn** | 学习稀疏模式 | O(n log n) | Reformer |
| **Block-sparse FlashAttention** | 块级稀疏，GPU友好 | O(n·k_blocks) | FlashAttention-3 |

## 5. 无限上下文 — 超越有限窗口

### 5.1 Infini-attention（Google DeepMind, 2024）

核心思想：在标准注意力之外增加"压缩记忆"模块，用线性注意力将历史压缩进固定大小的记忆状态。

```python
# Infini-attention 核心机制
class InfiniAttention(nn.Module):
    def __init__(self, dim, num_heads):
        self.dim = dim
        self.num_heads = num_heads
        
        # 压缩记忆状态: (batch, heads, d_key, d_value)
        self.memory = None
        self.memory_norm = None
    
    def forward(self, x, segment_id, use_memory=True):
        """
        混合注意力的两类输出:
        1. Local Attention: 当前segment内标准注意力
        2. Memory Retrieval: 从压缩记忆中检索
        """
        # 1. Local Attention (segment内)
        local_out = self.scaled_dot_product_attention(
            self.q_proj(x), self.k_proj(x), self.v_proj(x)
        )
        
        # 2. 从压缩记忆中检索
        if use_memory and self.memory is not None:
            # 记忆检索: Q × M^T
            Q = self.q_proj(x)
            memory_scores = torch.matmul(Q, self.memory.transpose(-2, -1))
            memory_scores = memory_scores / (self.memory_norm + 1e-8)
            memory_out = torch.matmul(
                nn.functional.elu(memory_scores) + 1,  # 线性化
                self.memory_values
            )
        
        # 3. 更新压缩记忆
        # M_new = M_old + σ(K)^T · V  (增量更新)
        K = nn.functional.elu(self.k_proj(x)) + 1  # 线性化激活
        V = self.v_proj(x)
        
        if self.memory is None:
            self.memory = torch.matmul(K.transpose(-2, -1), V)
            self.memory_norm = K.sum(dim=-2, keepdim=True)
        else:
            self.memory += torch.matmul(K.transpose(-2, -1), V)
            self.memory_norm += K.sum(dim=-2, keepdim=True)
        
        # 4. 门控融合local和memory输出
        gate = torch.sigmoid(self.gate_proj(x))
        return gate * local_out + (1 - gate) * memory_out
```

```

  - 状态空间模型 (SSM): h'(t) = A·h(t) + B·x(t), y(t) = C·h(t)
```

## 7. 生产实践 — 从理论到落地

### 7.1 预填-解码分离 (Prefill-Decode Disaggregation)

```
传统: 同一GPU既做prefill又做decode
  → 资源争抢
  → prefill是计算密集型，decode是内存密集型
  → 互相干扰

分离架构:
  Prefill节点 (计算密集型):
    - 高算力GPU (A100/H100)
    - 处理prompt输入
    - 生成KV Cache → 传递给Decode节点
    
  Decode节点 (内存密集型):
    - 大显存GPU
    - 接收KV Cache
    - 自回归生成token
    - 使用Continuous Batching提高吞吐

  调度器:
    - 动态分配Prefill/Decode节点
    - KV Cache通过NVLink/RDMA传输
    - 根据负载弹性扩缩
```

### 7.2 Continuous Batching

```python
# vLLM风格Continuous Batching
class ContinuousBatchingScheduler:
    """
    传统Static Batching: 等batch中所有请求完成才能处理新请求
    → 一个生成长文本的请求拖慢整批
    
    Continuous Batching: 
    - 每步迭代都可添加/移除请求
    - 完成的请求立即退出，新请求立即加入
    - 吞吐提升 5-10x
    """
    
    def step(self):
        """每一步运行"""
        running_seqs = self.get_running_sequences()
        waiting_seqs = self.get_waiting_sequences()
        
        # 1. 如果GPU有空闲，加入等待请求
        while self.has_free_memory() and waiting_seqs:
            seq = waiting_seqs.pop(0)
            self.allocate_kv_cache(seq)
            running_seqs.append(seq)
        
        # 2. 运行一步生成
        outputs = self.model.forward(running_seqs)
        
        # 3. 处理完成/超限的请求
        for seq, output in zip(running_seqs, outputs):
            if output.is_done or seq.len >= self.max_length:
                self.free_kv_cache(seq)
                running_seqs.remove(seq)
                self.return_to_client(seq)
```

### 7.3 Prefix Caching

```
场景: 多用户共享相同system prompt

自动Prefix Caching (APC):
  1. 计算system prompt的KV Cache
  2. 对所有使用相同system prompt的请求共享这份KV Cache
  3. 只计算用户独特部分的KV Cache
  
  节省: system prompt越长，节省越大
  典型system prompt: 500-2000 tokens
  节省Prefill时间: 30-60%

实现:
  - 基于内容哈希匹配前缀
  - 多请求共享引用计数
  - LRU淘汰不常用的前缀
```

```python
import llmlingua
compressor = llmlingua.PromptCompressor(
    model_name="microsoft/llmlingua-2-bert-base-multilingual",
    device_map="cuda"

compressed_prompt = compressor.compress_prompt(
    original_prompt,
    rate=0.5,  # 压缩比例
    force_tokens=["!", "?", "\n"]  # 保留关键分隔符

# 策略2: Selective Context — 按token重要性裁剪
# 基于self-attention信息熵判断token重要性
def selective_context_compression(tokens, attention_weights, budget):
    token_importance = attention_weights.mean(dim=-1).sum(dim=0)  # 聚合多层多头
    top_indices = token_importance.topk(budget).indices.sort()
    return tokens[top_indices]

# 策略3: 递归摘要 (Recursive Summarization)
def recursive_summarize(document, chunk_size=4000, summary_size=500):
    """将长文档分段摘要，再摘要摘要..."""
    chunks = [document[i:i+chunk_size] for i in range(0, len(document), chunk_size)]
    summaries = [summarize(chunk, max_tokens=summary_size) for chunk in chunks]
    
    while len("\n".join(summaries)) > chunk_size:
        summaries = recursive_summarize("\n".join(summaries), chunk_size, summary_size)
    
    return "\n".join(summaries)
```
