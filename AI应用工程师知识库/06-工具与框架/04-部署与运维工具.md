## 1. 部署方案对比

### 1.1 部署模式选型

| 模式 | 适用场景 | 优点 | 缺点 |
|------|----------|------|------|
| **Docker Compose** | 单机/开发测试 | 简单快速 | 无高可用 |
| **Kubernetes** | 企业级生产 | 高可用、弹性伸缩 | 复杂度高 |
| **Serverless** | 低频/事件驱动 | 按需付费、无运维 | 冷启动延迟 |
| **裸金属** | 极致性能 | 无虚拟化开销 | 运维复杂 |

### 1.2 选型决策

```
团队规模?
├── 小团队（<5人）
│   └── Docker Compose → 后期迁移K8s
├── 中团队（5-20人）
│   └── Kubernetes（托管版）
└── 大团队（>20人）
    └── 自建K8s + 完整DevOps

流量特征?
├── 稳定流量 → K8s Deployment
├── 波动大 → K8s + HPA自动伸缩
└── 低频触发 → Serverless（Knative/OpenFaaS）
```

## 2. Docker部署

### 2.1 基础镜像选择

| 镜像 | 适用场景 | 大小 |
|------|----------|------|
| `python:3.11-slim` | Python应用 | ~50MB |
| `python:3.11-alpine` | 极简Python | ~20MB |
| `openjdk:17-jdk-slim` | Java应用 | ~200MB |
| `nvidia/cuda:12.0-base` | GPU应用 | ~1GB |

### 2.2 Dockerfile最佳实践

**Python应用：**
```dockerfile
# 多阶段构建
FROM python:3.11-slim as builder

WORKDIR /app
COPY requirements.txt .
RUN pip install --user --no-cache-dir -r requirements.txt

# 运行阶段
FROM python:3.11-slim

WORKDIR /app
COPY --from=builder /root/.local /root/.local
COPY . .

ENV PATH=/root/.local/bin:$PATH
ENV PYTHONUNBUFFERED=1

EXPOSE 8000

CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```

**Java应用：**
```dockerfile
# 构建阶段
FROM maven:3.9-eclipse-temurin-17-alpine as builder
WORKDIR /app
COPY pom.xml .
COPY src ./src
RUN mvn clean package -DskipTests

# 运行阶段
FROM eclipse-temurin:17-jre-alpine
WORKDIR /app
COPY --from=builder /app/target/*.jar app.jar

EXPOSE 8080

ENTRYPOINT ["java", "-jar", "app.jar"]
```

## 3. Kubernetes部署

### 3.1 基础资源配置

**Deployment：**
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: ai-service
  labels:
    app: ai-service
spec:
  replicas: 3
  selector:
    matchLabels:
      app: ai-service
  template:
    metadata:
      labels:
        app: ai-service
    spec:
      containers:
        - name: ai-service
          image: ai-service:latest
          ports:
            - containerPort: 8000
          resources:
            requests:
              cpu: "500m"
              memory: "1Gi"
            limits:
              cpu: "2"
              memory: "4Gi"
          env:
            - name: OPENAI_API_KEY
              valueFrom:
                secretKeyRef:
                  name: ai-secrets
                  key: openai-api-key
          livenessProbe:
            httpGet:
              path: /health
              port: 8000
            initialDelaySeconds: 30
            periodSeconds: 10
          readinessProbe:
            httpGet:
              path: /ready
              port: 8000
            initialDelaySeconds: 5
            periodSeconds: 5
```

**Service：**

apiVersion: v1
kind: Service
metadata:

spec:

### 3.3 自动伸缩

**HPA（水平自动伸缩）：**
```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: ai-service-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: ai-service
  minReplicas: 2
  maxReplicas: 20
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
    - type: Pods
      pods:
        metric:
          name: http_requests_per_second
        target:
          type: AverageValue
          averageValue: "100"
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 60
      policies:
        - type: Percent
          value: 100
          periodSeconds: 15
```

**VPA（垂直自动伸缩）：**
```yaml
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: ai-service-vpa
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: ai-service
  updatePolicy:
    updateMode: "Auto"
  resourcePolicy:
    containerPolicies:
      - containerName: ai-service
        minAllowed:
          cpu: 100m
          memory: 512Mi
        maxAllowed:
          cpu: 4
          memory: 8Gi
```

### 4.2 Prometheus监控

**自定义指标：**
```python
from prometheus_client import Counter, Histogram, Gauge, start_http_server

# 定义指标
llm_requests_total = Counter(
    'llm_requests_total',
    'Total LLM requests',
    ['model', 'status']
)

llm_request_duration = Histogram(
    'llm_request_duration_seconds',
    'LLM request duration',
    ['model'],
    buckets=[0.1, 0.5, 1.0, 2.0, 5.0, 10.0]
)

llm_tokens_total = Counter(
    'llm_tokens_total',
    'Total tokens used',
    ['model', 'type']  # type: prompt/completion
)

active_sessions = Gauge(
    'active_sessions',
    'Number of active sessions'
)

# 使用
@llm_request_duration.time()
def call_llm(model, messages):
    response = llm_client.chat(model=model, messages=messages)
    
    llm_requests_total.labels(model=model, status="success").inc()
    llm_tokens_total.labels(model=model, type="prompt").inc(response.prompt_tokens)
    llm_tokens_total.labels(model=model, type="completion").inc(response.completion_tokens)
    
    return response
```

**Prometheus配置：**
```yaml
# prometheus.yml
global:
  scrape_interval: 15s

scrape_configs:

      - targets: ['ai-service:8000']
    metrics_path: /metrics
  
  - job_name: 'vllm'
    static_configs:
      - targets: ['vllm:8000']
```

## 5. 日志管理

### 5.1 结构化日志

```python
import structlog
import logging

# 配置
structlog.configure(
    processors=[
        structlog.stdlib.filter_by_level,
        structlog.stdlib.add_logger_name,
        structlog.stdlib.add_log_level,
        structlog.stdlib.PositionalArgumentsFormatter(),
        structlog.processors.TimeStamper(fmt="iso"),
        structlog.processors.StackInfoRenderer(),
        structlog.processors.format_exc_info,
        structlog.processors.JSONRenderer()
    ],
    context_class=dict,
    logger_factory=structlog.stdlib.LoggerFactory(),
    wrapper_class=structlog.stdlib.BoundLogger,
    cache_logger_on_first_use=True,
)

logger = structlog.get_logger()

# 使用
logger.info(
    "llm_request_completed",
    model="gpt-4o",
    latency_ms=1500,
    tokens_prompt=1000,
    tokens_completion=500,
    user_id="user_123",
    session_id="sess_456"
)
```

## 6. CI/CD流水线

### 6.1 GitHub Actions

```yaml
name: AI Service CI/CD

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      
      - name: Setup Python
        uses: actions/setup-python@v5
        with:
          python-version: '3.11'
      
      - name: Install dependencies
        run: |
          pip install -r requirements.txt
          pip install -r requirements-dev.txt
      
      - name: Lint
        run: flake8 .
      
      - name: Unit tests
        run: pytest tests/unit/ -v --cov=app --cov-report=xml
      
      - name: Integration tests
        run: pytest tests/integration/ -v
        env:
          OPENAI_API_KEY: ${{ secrets.OPENAI_API_KEY_TEST }}

  build:
    needs: test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      
      - name: Build Docker image
        run: docker build -t ai-service:${{ github.sha }} .
      
      - name: Push to registry
        run: |
          echo ${{ secrets.DOCKER_PASSWORD }} | docker login -u ${{ secrets.DOCKER_USERNAME }} --password-stdin
          docker push ai-service:${{ github.sha }}

  deploy:
    needs: build
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main'
    steps:
      - name: Deploy to K8s
        run: |
          kubectl set image deployment/ai-service ai-service=ai-service:${{ github.sha }}
          kubectl rollout status deployment/ai-service
```

### 7.2 常见陷阱

**陷阱1：无资源限制**
- 问题：Pod占用过多资源影响其他服务
- 解决：始终设置resources.limits

**陷阱2：忽视健康检查**
- 问题：故障Pod未及时发现
- 解决：配置liveness/readiness探针

**陷阱3：日志未结构化**
- 问题：日志难以查询分析
- 解决：使用JSON结构化日志

## 深度分析

AI应用的部署与运维相比传统微服务面临额外的复杂性：GPU资源调度、LLM推理的延迟敏感性和成本波动都需要专门的设计。部署模式的选择应与团队规模相匹配——小团队优先Docker Compose降低复杂度，中大型团队则建议采用Kubernetes托管版以兼顾弹性与运维成本。Serverless模式在低频、事件驱动的场景下具有显著成本优势，但冷启动问题在延迟敏感型AI应用中需要审慎评估。

可观测性是AI应用运维的基石。Prometheus + Grafana的组合覆盖了指标采集与可视化，而结构化日志（JSON格式）配合ELK/Loki则提供了日志分析的基础。值得重点关注的是LLM专有指标——Token消耗、模型级联调用链、语义缓存命中率——这些指标对AI应用的成本治理和质量调优至关重要。

CI/CD流水线中应包含评估测试阶段。与普通应用的CI/CD不同，AI应用的部署前必须运行回归评估，确保模型更新或Prompt调整未导致质量回退。GitOps（ArgoCD）模式在Kubernetes部署中推荐采用，其声明式配置和自动化同步机制可以有效降低部署风险。
