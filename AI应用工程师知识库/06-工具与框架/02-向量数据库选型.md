## 1. 向量数据库概述

### 1.1 为什么需要向量数据库？

**传统数据库的局限：**
- 无法高效存储高维向量（768/1024/1536维）
- 无法快速相似度检索（暴力搜索O(n)太慢）

**向量数据库的核心能力：**
- 高维向量存储
- 近似最近邻搜索（ANN）
- 混合检索（向量+元数据过滤）
- 高并发、低延迟

### 1.2 核心概念

| 概念 | 说明 |
|------|------|
| **Embedding** | 文本/图像转换为高维向量 |
| **相似度度量** | 余弦相似度、欧氏距离、点积 |
| **ANN算法** | HNSW、IVF、PQ等近似搜索算法 |
| **召回率** | 检索结果中包含正确答案的比例 |

### 2.2 Milvus

**定位：** 企业级开源向量数据库

**架构：**
```
Milvus Cluster
├── Proxy（查询入口）
├── Query Node（查询执行）
├── Data Node（数据写入）
├── Index Node（索引构建）
└── MinIO/S3（对象存储）
```

**适用场景：**
- 十亿级向量规模
- 高并发查询（>1000 QPS）
- 需要分布式扩展
- 混合检索（向量+标量过滤）

**核心特性：**
- 支持多种索引类型（HNSW、IVF_FLAT、IVF_SQ8）
- 分区与分片
- 多副本高可用
- 丰富的SDK（Python/Java/Go/Node.js）

**代码示例：**
```python
from pymilvus import connections, Collection, FieldSchema, CollectionSchema, DataType

# 连接
connections.connect(host='localhost', port='19530')

# 定义集合
fields = [
    FieldSchema(name="id", dtype=DataType.INT64, is_primary=True),
    FieldSchema(name="embedding", dtype=DataType.FLOAT_VECTOR, dim=1536),
    FieldSchema(name="text", dtype=DataType.VARCHAR, max_length=65535),
    FieldSchema(name="category", dtype=DataType.VARCHAR, max_length=128),
]
schema = CollectionSchema(fields, "知识库")
collection = Collection("knowledge_base", schema)

# 创建索引
index_params = {
    "metric_type": "COSINE",
    "index_type": "HNSW",
    "params": {"M": 16, "efConstruction": 200}
}
collection.create_index("embedding", index_params)

# 插入数据
collection.insert([
    [1, 2, 3],  # id
    [[0.1, 0.2, ...], [0.3, 0.4, ...], ...],  # embedding
    ["文本1", "文本2", ...],  # text
    ["技术", "产品", ...]  # category
])

# 搜索
collection.load()
results = collection.search(
    data=[[query_embedding]],
    anns_field="embedding",
    param={"metric_type": "COSINE", "params": {"ef": 64}},
    limit=10,
    expr='category == "技术"',  # 元数据过滤
    output_fields=["text", "category"]
)
```

**部署模式：**
| 模式 | 适用场景 | 资源 |
|------|----------|------|
| Standalone | 开发测试 | 单机 |
| Cluster | 生产环境 | 3+节点 |
| Milvus Lite | 边缘/嵌入式 | 无依赖 |

### 2.3 pgvector

**定位：** PostgreSQL的向量扩展

**适用场景：**
- 已有PostgreSQL基础设施
- 向量数据量不大（<1000万）
- 需要事务支持
- 需要JOIN操作

**核心特性：**
- 与PG完全集成
- 支持ACID事务
- 支持复杂SQL查询
- 无需额外运维

**代码示例：**
```sql
-- 启用扩展
CREATE EXTENSION vector;

-- 创建表
CREATE TABLE documents (
    id SERIAL PRIMARY KEY,
    content TEXT,
    embedding vector(1536),
    metadata JSONB,
    created_at TIMESTAMP DEFAULT NOW()
);

-- 创建向量索引（HNSW）
CREATE INDEX ON documents USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64);

-- 插入数据
INSERT INTO documents (content, embedding, metadata)
VALUES ('文本内容', '[0.1, 0.2, ...]', '{"category": "技术"}');

-- 相似度搜索
SELECT id, content, 1 - (embedding <=> '[query_vector]') AS similarity
FROM documents
WHERE metadata->>'category' = '技术'
ORDER BY embedding <=> '[query_vector]'
LIMIT 10;
```

**Python集成：**
```python
import psycopg2

conn = psycopg2.connect("dbname=mydb user=postgres")
cur = conn.cursor()

# 使用LangChain
from langchain_community.vectorstores import PGVector

vectorstore = PGVector(
    connection_string="postgresql://user:pass@localhost/mydb",
    embedding_function=embeddings,
    collection_name="knowledge_base"
)
```

**优缺点：**

| 优点 | 缺点 |
|------|------|
| 与现有PG无缝集成 | 大规模性能不如专用向量库 |
| 无需额外运维 | 高并发下性能受限 |
| 支持复杂查询 | 向量索引类型有限 |
| 事务支持 | |

### 2.4 Pinecone

**定位：** 全托管向量数据库SaaS

**适用场景：**
- 快速启动，无需运维
- 中小规模（<1亿向量）
- 预算充足

**核心特性：**
- 完全托管，零运维
- 自动扩缩容
- 元数据过滤
- 混合搜索

**代码示例：**
```python
from pinecone import Pinecone, ServerlessSpec

# 初始化
pc = Pinecone(api_key="your-api-key")

# 创建索引
index_name = "knowledge-base"
pc.create_index(
    name=index_name,
    dimension=1536,
    metric="cosine",
    spec=ServerlessSpec(cloud="aws", region="us-east-1")
)

# 连接索引
index = pc.Index(index_name)

# 插入数据
index.upsert(vectors=[
    {
        "id": "doc1",
        "values": [0.1, 0.2, ...],
        "metadata": {"category": "技术", "source": "doc1.pdf"}
    }
])

# 查询
results = index.query(
    vector=[query_vector],
    top_k=10,
    filter={"category": {"$eq": "技术"}},
    include_metadata=True
)
```

**定价：**
- Starter: 免费（5万向量）
- Standard: $0.096/小时 + $0.10/百万查询
- Enterprise: 定制

### 2.5 Chroma

**定位：** 嵌入式向量数据库

**适用场景：**
- 开发测试
- 原型验证
- 轻量级应用
- 边缘设备

**核心特性：**
- 纯Python，pip安装
- 无需外部依赖
- 支持持久化
- 简单易用

**代码示例：**
```python
import chromadb

# 内存模式（开发）
client = chromadb.Client()

# 持久化模式（生产）
client = chromadb.PersistentClient(path="./chroma_db")

# 创建集合
collection = client.create_collection(name="knowledge_base")

# 添加文档
collection.add(
    documents=["文本1", "文本2"],
    metadatas=[{"category": "技术"}, {"category": "产品"}],
    ids=["doc1", "doc2"]
)

# 查询
results = collection.query(
    query_texts=["查询内容"],
    n_results=10,
    where={"category": "技术"}
)
```

**优缺点：**

| 优点 | 缺点 |
|------|------|
| 极简安装使用 | 不适合大规模生产 |
| 无需运维 | 性能一般 |
| 与LangChain集成好 | 功能相对简单 |

## 3. 选型决策指南

### 3.1 决策树

```
数据规模?
├── < 10万条
│   └── Chroma（开发）/ pgvector（生产）
├── 10万 - 1000万条
│   ├── 已有PostgreSQL? → pgvector
│   └── 新项目 → Milvus / Qdrant
├── 1000万 - 1亿条
│   ├── 不想运维? → Pinecone
│   └── 自运维 → Milvus / Qdrant
└── > 1亿条
    └── Milvus（分布式集群）

查询QPS?
├── < 100 QPS → 任意
├── 100 - 1000 QPS → Milvus / Qdrant
└── > 1000 QPS → Milvus集群
```

### 3.2 场景化选型

| 场景 | 推荐 | 理由 |
|------|------|------|
| **快速原型** | Chroma | 零配置，快速验证 |
| **已有PG系统** | pgvector | 无缝集成，无额外运维 |
| **企业级RAG** | Milvus | 功能全面，性能优秀 |
| **无运维团队** | Pinecone | 全托管，省心 |
| **高性能要求** | Qdrant | Rust实现，性能极致 |
| **混合搜索** | Weaviate | 向量+关键词一体化 |

## 4. 性能优化

### 4.1 索引选择

| 索引类型 | 构建速度 | 查询速度 | 召回率 | 内存占用 | 适用场景 |
|----------|----------|----------|--------|----------|----------|
| **FLAT** | 快 | 慢 | 100% | 低 | 小数据集（<10万） |
| **IVF_FLAT** | 中等 | 中等 | 高 | 中等 | 平衡选择 |
| **IVF_SQ8** | 中等 | 快 | 较高 | 低 | 内存受限 |
| **HNSW** | 慢 | 快 | 高 | 高 | 生产推荐 |

### 4.2 参数调优

**HNSW参数：**
```python
# M: 每个节点的最大连接数
# 越大 → 召回率越高，构建越慢，内存越大
# 推荐：8-32

# efConstruction: 构建时的搜索范围
# 越大 → 图质量越高，构建越慢
# 推荐：64-200

# ef: 查询时的搜索范围
# 越大 → 召回率越高，查询越慢
# 推荐：64-512
```

### 5.2 常见陷阱

**陷阱1：忽视元数据过滤性能**
- 问题：大量向量+复杂过滤查询慢
- 解决：选择支持高效过滤的数据库（Milvus、Qdrant）

**陷阱2：索引参数不当**
- 问题：召回率太低或构建太慢
- 解决：根据数据规模调参，充分测试

**陷阱3：忽视数据增长**
- 问题：初期选型未考虑扩展性
- 解决：预留10倍增长空间

## 深度分析

向量数据库的选型本质上是对数据规模、查询性能、运维成本的三角权衡。专用向量库（Milvus/Qdrant）在大规模和高并发场景下优势明显，但其分布式架构的运维复杂度不可忽视。对于已深度使用PostgreSQL的团队，pgvector提供了最低摩擦的向量存储方案，在中低规模场景下完全可以胜任。

索引策略是向量数据库性能的核心杠杆。HNSW索引在生产环境中最为推荐，其参数调优（M、efConstruction、ef）直接决定了检索精度与延迟的平衡。实践中，建议结合业务场景的召回率要求进行充分压测，而非照搬默认参数。元数据过滤的性能往往被低估——在混合检索场景下，过滤效率可能成为真正的瓶颈。

选型时还应预留数据增长空间，建议按当前规模的3-5倍评估。对于快速迭代的初创项目，优先考虑Pinecone或Chroma以降低初期运维负担，待业务稳定后再评估迁移至Milvus等自管方案。数据库与框架的集成成熟度也应纳入考量——LangChain等框架对特定数据库的深度集可能大幅降低开发成本。
