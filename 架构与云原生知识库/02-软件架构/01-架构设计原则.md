## 1. SOLID原则

### 1.1 单一职责原则（SRP）

一个模块/类只应有一个变更理由。

### 1.2 开闭原则（OCP）

对扩展开放，对修改关闭。用接口/抽象解耦。

### 1.3 里氏替换原则（LSP）

子类必须能替换父类，而不改变程序正确性。

### 1.4 接口隔离原则（ISP）

接口应小而专，避免胖接口。

### 1.5 依赖反转原则（DIP）

依赖抽象而非具体实现。

**在架构层：**
```python
# ❌ 高层模块直接依赖低层
class ReportService:
    def __init__(self):
        self.db = MySQLDatabase()  # 硬编码

# ✅ 依赖抽象
class ReportService:
    def __init__(self, db: Database):
        self.db = db  # 可替换任何Database实现
```

## 2. 架构核心原则

### 2.1 关注点分离

每个模块只关注一个特定功能维度，模块间通过清晰接口通信。

### 2.2 高内聚低耦合

| 概念 | 说明 | 度量 |
|------|------|------|
| 内聚 | 模块内部元素的相关程度 | 高内聚 = 功能紧密相关 |
| 耦合 | 模块之间的依赖程度 | 低耦合 = 独立性强 |

### 2.3 分层架构原则

- 上层依赖下层
- 同层可相互调用
- 下层不能依赖上层

### 2.4 康威定律

> 系统的架构会反映构建它的组织的沟通结构。

**启示：** 组织结构和沟通方式直接影响架构设计。

## 3. 架构风格对比

| 风格 | 特点 | 适合场景 |
|------|------|---------|
| 单体 | 单一部署单元 | 小团队，早期产品 |
| 分层 | 水平分层，各司其职 | 企业应用 |
| 微服务 | 独立服务，独立部署 | 大团队，复杂业务 |
| 事件驱动 | 异步事件通信 | 高伸缩，解耦需求 |
| 无服务器 | 函数即服务 | 事件处理，轻量API |
| 六边形 | 端口适配器模式 | 领域驱动设计 |

### 架构演进的典型路径

```
单体 → 分层 → 微服务 → 事件驱动/网格
（随规模和复杂度递增）
```

## 4. 设计决策方法

### 4.1 架构决策记录（ADR）

每项重要决策记录：

```
ADR-001: 选择 PostgreSQL 作为主数据库
状态: 已采纳
背景: 需要强事务支持，团队熟悉SQL
决策: 使用 PostgreSQL 15
后果: 需考虑未来读写分离方案
```

### 4.2 决策权衡矩阵

| 方案 | 性能 | 可维护性 | 学习成本 | 生态 |
|------|------|----------|----------|------|
| 方案A | 高 | 中 | 低 | 丰富 |
| 方案B | 中 | 高 | 高 | 中等 |
| 方案C | 低 | 高 | 低 | 丰富 |

### 4.3 过度工程警告

- 不要为可能永远不会出现的问题设计解决方案
- YAGNI：You Aren't Gonna Need It
- 适度设计，持续演进

## 5. 架构文档

### 5.1 C4模型

| 层级 | 描述 | 受众 |
|------|------|------|
| Context | 系统上下文图 | 所有人 |
| Container | 容器图（服务/数据库等） | 技术团队 |
| Component | 组件图 | 开发者 |
| Code | 类图（可选） | 开发者 |

### 5.2 架构文档要点

```yaml
系统名称：订单系统
架构风格：微服务 + 事件驱动
技术栈：
  - 运行时：Go 1.22
  - 数据库：PostgreSQL 15, Redis 7
  - 消息队列：Kafka 3.5
  - 部署：Kubernetes + ArgoCD
关键决策：
  - 使用 Saga 模式处理分布式事务
  - 事件采用 Avro 序列化+Schema Registry
```
