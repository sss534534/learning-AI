## 1. 分层架构模式

### 1.1 经典四层架构

```
表示层（API/UI）
    ↓
应用层（Use Case）
    ↓
领域层（业务规则）
    ↓
基础设施层（DB/外部服务）
```

### 1.2 依赖方向

- 上层依赖下层
- 每层只与相邻层通信
- 上层是"知道"方向，下层是"被使用"方向

### 1.3 局限

- 随着复杂度增加，层间边界模糊
- 可能退化为"大盘鸡"架构
- 不适合高复杂度的业务逻辑

## 2. 事件驱动架构

### 2.1 核心组件

| 组件 | 职责 |
|------|------|
| 事件生产者 | 发布事件 |
| 事件通道 | 消息队列/事件流 |
| 事件消费者 | 处理事件 |
| 事件存储 | 持久化事件历史 |

### 2.2 编排 vs 编制

| 模式 | 描述 | 特点 |
|------|------|------|
| 编排（Orchestration） | 中央协调器指挥 | 强耦合，可见 |
| 编制（Choreography） | 各服务自主响应 | 去中心，松耦合 |

### 2.3 Saga模式

```python
# Saga 编排器
class OrderSaga:
    def execute(self, order):
        try:
            inventory_service.reserve(order.items)
            payment_service.charge(order.total)
            order_service.confirm(order.id)
        except Exception:
            inventory_service.compensate(order.items)
            payment_service.refund(order.total)
            order_service.cancel(order.id)
```

## 3. CQRS与事件溯源

### 3.1 CQRS

命令查询职责分离：

```
写模型（Command）→ 更新数据
读模型（Query）  → 读取数据（可优化为独立存储）
```

### 3.2 事件溯源

不存储当前状态，存储所有事件序列：

```
事件流：
OrderCreated → ItemAdded → ItemAdded → PaymentReceived → OrderShipped
                                            ↓
                                  当前状态由事件重放计算
```

```python
class OrderEventSourced:
    def __init__(self):
        self.events = []
        self.status = None

    def apply_event(self, event):
        if isinstance(event, OrderCreated):
            self.status = "PENDING"
        elif isinstance(event, OrderShipped):
            self.status = "SHIPPED"

    def replay(self, events):
        for event in events:
            self.apply_event(event)
```

### 3.3 CQRS+ES适用场景

| 适合 | 不适合 |
|------|--------|
| 审计需求强烈 | 简单CRUD |
| 复杂业务规则 | 实时查询要求高 |
| 需要完整历史 | 存储成本敏感 |

## 4. 六边形架构

### 4.1 端口-适配器模式

```
     [外部输入] ← 适配器 → ╔═══════════╗ ← 适配器 → [外部输出]
     [HTTP]     → Controller ║           ║ Repository → [DB]
     [CLI]      → Handler   ║  核心领域  ║ Publisher  → [MQ]
     [gRPC]     → Service   ║           ║ Client     → [API]
                            ╚═══════════╝
                               端口接口
```

**特点：**
- 核心领域与基础设施解耦
- 所有外部依赖通过适配器接入
- 方便测试（mock适配器即可）

### 4.2 代码结构

```
src/
├── domain/          # 领域层（核心，无外部依赖）
│   ├── model/
│   ├── service/
│   └── repository/  # 接口（端口）
├── application/     # 应用层
│   └── usecase/
└── infrastructure/  # 基础设施（适配器）
    ├── persistence/
    ├── messaging/
    └── web/
```

## 5. 架构最佳实践

### 5.1 质量属性

| 属性 | 描述 | 实现方法 |
|------|------|---------|
| 可用性 | 系统正常运行时间 | 冗余，故障转移，健康检查 |
| 可扩展性 | 处理增长的负载 | 水平扩展，无状态设计 |
| 可维护性 | 修改和扩展的容易度 | 清晰边界，自动化测试 |
| 安全性 | 保护数据和系统 | 认证，授权，加密，审计 |
| 性能 | 响应时间/吞吐量 | 缓存，异步，优化查询 |

### 5.2 架构演进原则

1. **演进优于预测**：不要为未来过度设计
2. **自动化优先**：CI/CD，测试，基础设施
3. **可观测性内置**：日志，指标，追踪从第一天开始
4. **失败设计**：假设一切会失败（断路，重试，降级）
5. **数据保护**：加密，备份，灾备

### 5.3 反模式清单

| 反模式 | 表现 | 解决方案 |
|--------|------|---------|
| 大泥球 | 架构混乱，没有清晰边界 | 逐步重构+定义边界 |
| 上帝类 | 一个类承担过多职责 | SRP拆分 |
| 分布式单体 | 伪微服务，共享数据库 | 数据解耦+服务边界 |
| 过度抽象 | 不必要的间接层 | YAGNI，移除不需要的抽象 |
